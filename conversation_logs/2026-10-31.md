## 1. 메인(경기용) 코드 구조

### 폴더 = 역할

| 폴더 (`include/`, `src/`) | 하는 일 | 대표 모듈 |
|---|---|---|
| `app/` | 부팅 순서 | `BootManager` |
| `hardware/` | 핀 초기화, 리셋 원인 | `BoardIo`, `ResetManager` |
| `interrupts/` | SW1·SW2 인터럽트 | `ButtonInterrupts` |
| `system/` | 안전 상태, 배터리, 로그, LED | `SystemManager`, `BatteryMonitor`, `EventLogger`, `StatusLed` |
| `sensors/` | 바닥 센서 4개 I2C, 색 판별, 교정값 | `SensorManager` → `ColorSensorManager` → `FloorColorClassifier`, `CalibrationStore` |
| `communication/` | 라즈베리파이 UART 패킷 | `RaspberryLink` |
| `control/` | 전략과 구동 변환 | `RobotFsm`, `DriveLogic` |
| `motor/` | 모터 출력, 브레이크, 만료 감시 | `MotorController` → `Bts7960Driver` |

설정값은 모두 `*_config.hpp`와 `pins.hpp`/`pins_v2.hpp`에 모여 있습니다.

### `loop()` 한 바퀴 (`src/main.cpp`)

```text
① SystemManager::update        안전 상태 확인
② RaspberryLink::poll          라즈 UART 읽기 (최대 128바이트)
③ SensorManager::update        바닥 센서 짧은 I2C 한 단계
④ BatteryMonitor::update       V2: 전원 투입 후 3초 동안만 배터리 판정
⑤ SystemManager::update        안전 재확인 (일부러 두 번)
⑥ 센서 스냅샷 + 라즈 최신값
⑦ RobotFsm::update             → 의도 (탐색, 접근, 공격, 위험구역 회피 …)
⑧ DriveLogic::makeCommand      → 모터 명령 (80ms 기한)
⑨ 움직임 허용이면 MotorController::apply, 아니면 brake
⑩ LED, 로그 출력, delay(1)
```

### 루프 밖의 안전 경로 (루프가 멈춰도 동작)

- **SW1 인터럽트:** 즉시 EN을 LOW로 내리고 영구 정지합니다. 재부팅 전까지 풀리지 않습니다.
- **모터 만료 감시 태스크:** 5ms마다 명령 기한을 확인하고, 지나면 브레이크를 겁니다.

```text
센서 ─┐
라즈 ─┼─▶ 스냅샷 ─▶ FSM ─▶ DriveLogic ─▶ MotorController ─▶ BTS7960
       │                                      ▲

```

## 2. 벤치 코드 구조

벤치는 **경기용 루프에서 FSM 자리만 `BenchController`로 바꾼 것**입니다. 안전, 센서, 라즈, 배터리, 모터 모듈은 경기용과 똑같은 것을 씁니다.

```text
경기용:  … 센서·라즈 ─▶ RobotFsm + DriveLogic ─▶ 모터
벤치:    … 센서·라즈 ─▶ BenchController       ─▶ 모터 (최대 20%)
                         ▲
                   console() ← UART0 명령 (MODE / DRIVE / STOP …)
```

### 파일 구성

| 파일 | 역할 |
|---|---|
| `src/bench_main.cpp` | 진입 파일입니다. 콘솔 입력, 명령 해석, 로그 출력, `setup`/`loop`가 모두 여기에 있습니다 (V1과 `robot_bench_v2` 공용) |
| `include/bench/bench_controller.hpp` + `src/bench/bench_controller.cpp` | 모드별로 모터 명령을 만듭니다 |
| `include/bench/bench_config.hpp` | 출력 상한 20%, DRIVE 유지 250ms, 로그 주기 100ms 등 |
| `tools/bench_console.py`, `tools/bench_gui.py` | PC 쪽 도구입니다. GUI는 아직 제 작업 폴더에만 있습니다 |

### BenchController 모드

| 모드 | 동작 |
|---|---|
| `STOP` | 정지 |
| `MOTOR` | 정해진 순서로 바퀴마다 3초씩 저출력 구동한 뒤 `DONE MOTOR` |
| `MANUAL` | `DRIVE l r`을 250ms 안에 계속 받아야 움직입니다 |
| `DATA` | 모터 없이 센서 값만 봅니다 |
| `ALIGN` / `FOLLOW` | 라즈 목표를 보고 정렬하거나 따라갑니다 |
| `AVOID` | 바닥 위험색에서 피합니다 |

### 벤치 `loop()`

경기용 ①–⑤와 똑같이 시작합니다. 그다음 `console()`이 명령을 읽고, `BenchController::update`가 명령을 만들고, 허용이면 apply, 아니면 brake합니다. 마지막에 LED, 로그, BAT 줄, 상태 줄(`D,`, `S,`)을 출력합니다. 출력은 UART 버퍼에 자리가 없으면 기다리지 않고 건너뜁니다.

### 공통 안전 규칙

- MODE를 바꾸거나 STOP한 뒤에는 SW2를 다시 눌렀다 떼야 움직입니다.
- 잘못된 명령이 오면 바로 정지합니다.
- 글자 사이가 250ms 넘게 벌어지면 그 줄을 버리고 정지합니다.

- **높이 3개는 꼭 있어야 합니다.** 이 센서는 자체 LED 빛이 바닥에 반사된 것을 읽어서, 간격이 멀어지면 밝기가 크게 떨어집니다. 가장 걱정하던 "20mm에서 유색 바닥을 검정으로 오인"을 막는 방법이 바로 20mm 기준값을 따로 재 두는 것입니다.

## 1. 센서 프로필 (프리셋)

**프로필은 바닥 센서 설정값 묶음 하나에 이름을 붙인 것입니다.**

| 값 | 지금 (시작값, 실물 미검증) | 무엇이 바뀌나 |
|---|---|---|
| 수광 시간 | 약 5ms | 길수록 밝게 읽히지만 측정이 느려짐 |
| 게인(민감도) | X16 | 높을수록 멀리 있는 바닥에 강하지만 가까우면 포화 |
| LED 전류 | 20mA | 높을수록 밝음, 열과 포화 위험 |

**프리셋 예시** (값은 제 제안이라 학현이 정해야 합니다)

- `P0 기본`: 지금 값 그대로 (5ms, X16, 20mA). 아무것도 안 고르면 이것입니다.
- `P1 근접`: 3mm에서 포화가 날 때. 게인 또는 LED를 낮춤 (예: X8, 12mA)
- `P2 원거리`: 20mm에서 유색이 검정으로 읽힐 때. 게인 또는 수광 시간을 높임 (예: X32 또는 8ms)

**경기용 펌웨어**
- `sensor_config.hpp`에서 한 줄(`SENSOR_PROFILE = P0`)로 고르고, 프로필마다 값을 표로 둡니다.
- 경기 중에는 바뀌지 않습니다(컴파일할 때 고정).

**벤치 펌웨어**
- 다시 올리지 않고 `PROFILE 1` 같은 명령으로 바로 바꿔 봅니다.
- GUI에 프로필 선택 칸을 두고, 3/10/20mm에서 밝기를 비교해서 어느 프로필이 맞는지 고르게 합니다.

**교정값은 프로필별로 따로 저장합니다.**
- 지금은 설정이 바뀌면 교정이 무효가 됩니다. 앞으로는 프로필마다 NVS에 자리를 따로 둬서, 바꿨다가 돌아와도 기존 교정이 살아 있게 합니다.

| **배터리 전압 ADC** | 측정값이 튐 | 전원 투입 후 3초 동안만 측정하므로 모터가 돌기 전이라 영향 적음 |
| **라즈↔ESP32 UART** (CRC 없음) | 깨진 바이트 | 헤더, 길이, 상태 비트, 좌표 범위 검사로 대부분 걸러짐. **범위 안에서 숫자만 바뀐 깨짐은 못 잡음** (CRC를 안 쓰기로 한 것은 결정 사항이라 그대로 둠) |
| **라즈5** | 전압 저하 → 성능 제한, 최악은 재부팅 | 영상 처리가 느려지거나 끊김. ESP32는 이걸 "라즈 끊김"으로 보고 탐색 동작으로 넘어감 (설계대로) |
| **PiCam3** (CSI 리본선) | 화면 줄무늬, 프레임 누락, 카메라 시간 초과 | 목표 검출이 흔들리거나 끊김 |

## 대책 (효과가 크고 쉬운 순서)

1. **모터 단자마다 0.1µF 세라믹 콘덴서:** 단자 두 개 사이에 하나, 각 단자와 모터 몸체 사이에 하나씩 답니다. 브러시 노이즈를 줄이는 가장 흔하고 효과적인 방법입니다.
2. **선을 꼬기:** 모터선 두 가닥, 배터리선 두 가닥을 각각 꼬아서 짧게 씁니다(화요일에 12AWG로 바꿀 때 같이).
3. **선 떨어뜨리기:** 모터선·전원선과 센서선, UART선, 카메라 리본선을 서로 멀리 둡니다. 꼭 만나야 하면 직각으로 지나가게 합니다. 이번 합선 대책인 선 고정 홈을 낼 때 함께 반영하면 됩니다.
4. **드라이버 전원 입력에 큰 전해 콘덴서(수백 µF):** BTS7960 바로 옆에 달면 순간 전압 저하가 줄어듭니다.
5. **라즈5 전원:** 라즈5는 5V 5A가 필요하고 전압이 떨어지면 성능을 스스로 낮춥니다. USB-C 선에 페라이트 코어를 달고, 전원을 주는 컨버터 용량이 충분한지 확인하세요.
6. **접지:** 모터 전류가 ESP32나 센서 GND를 지나가지 않게, 모터 전원 리턴은 배터리로 바로 가는 게 좋습니다. V2 기판에서 이게 어떻게 돼 있는지는 원하시면 기판 파일을 확인하겠습니다.

## 측정 방법 (새 시험 프로그램으로 가능)

벤치에서 모터를 돌리면서 로그를 보면 됩니다.
- `LINK` 줄의 `invalidPackets`: 라즈를 연결했을 때 UART가 깨지는지
- `S` 줄의 오류 값: 0이 아니면 그 센서 I2C 문제
- `I` 줄의 `busErrors`: IMU I2C 오류
- `SYSTEM` 줄의 리셋 원인: 브라운아웃으로 재부팅됐는지
- 라즈 쪽: `vcgencmd get_throttled`(0x0이 아니면 전압 저하 기록), `dmesg`의 카메라 오류

**주의:** 벤치 펌웨어는 출력을 20%로 제한해서 실제 경기(최대 65%)나 밀다가 구속될 때보다 노이즈가 훨씬 작습니다. 그래서 벤치에서 문제가 없어도 안심할 수 없습니다. **11/4 이후 경기 펌웨어로 바닥에서 밀기 시험을 할 때** 같은 항목을 꼭 다시 확인하세요. 그때 센서 채널이 꺼지는 일이 생기면, 그 정책을 바꿀지는 학현과 따로 검토할 일입니다. 지금 정책은 의도된 안전 설계라 임의로 바꾸지 않습니다.

- **전원 구조:** 라즈는 V2 기판의 벅 컨버터에서 USB-C 선으로 전원을 받고, 배터리는 모터와 같이 씁니다.
  - 4S 배터리가 모터 때문에 출렁여도 벅 입력이 충분히 높게 유지되면 5V 자체는 버팁니다.
  - 그래도 위 사례처럼 **순간 강하, 벅 용량 부족, USB-C 선 품질, GND 흔들림**은 그대로 위험합니다.
- **이미 전원 사고가 있었습니다:** 라즈 1대가 J19 5.1V 경로로 고장 났습니다. 그래서 USB-C로만 전원을 주기로 한 것입니다.
- **경기 중 영향:**
  - **스로틀링:** 영상 처리가 느려집니다. ESP32는 프레임이 늦게 오면 "영상 끊김"으로 판단해 공격하지 못하고 탐색으로 갑니다.
  - **재부팅:** 라즈가 다시 켜질 때까지 수십 초 동안 카메라 없이 싸웁니다. 설계상 탐색과 위험구역 회피는 계속하지만 공격 능력은 사라집니다.
  - 그래서 **라즈 송신 프로그램은 부팅하면 자동으로 시작되게** 만들어야 합니다. 나중에 송신 코드를 만들 때 꼭 넣어야 할 항목입니다.

## 확인 방법

1. **모터 시험 직후 라즈에서 확인합니다.**
   ```bash
   vcgencmd get_throttled
   ```
   `0x0`이면 정상입니다. `0x50000`처럼 0이 아니면 전압 저하나 스로틀링이 있었다는 기록입니다. `dmesg`에서 undervoltage 메시지도 확인하세요.
2. **멀티미터로 라즈 GPIO 핀 사이의 전압을 잽니다.** 2번 핀(5V)과 6번 핀(GND)입니다. 벅 출력이 아니라 라즈 쪽에서 재야 합니다. 모터를 출발시키거나 구속할 때 4.75V 아래로 떨어지면 문제입니다. 순간 강하는 멀티미터로는 잘 안 잡히니 `get_throttled` 기록이 더 믿을 만합니다.
3. **벅 컨버터(U2)의 정격 전류**가 라즈5 최대치(약 5A)에 맞는지 부품 사양을 확인하세요.

## 대책 (쉬운 순서)

1. **모터 단자에 0.1µF 콘덴서:** 카메라 대책과 같은 것으로, 근원을 줄입니다.
2. **라즈 USB-C 입력 근처와 벅 출력에 세라믹 콘덴서:** 이미 있는 큰 전해 콘덴서에 더해서 답니다.
3. **USB-C 선은 짧고 굵은 정품으로:** 잘라서 이은 선이나 연장선은 피합니다.
4. **모터 리턴 전류가 라즈와 센서 GND를 지나가지 않게 배선합니다.**
5. **위 방법으로도 안 되면** 라즈만 따로 작은 배터리를 쓰는 방법이 있습니다. 여러 사례에서 확실한 해결책이었지만, 부품이 하나 늘고 무게도 늘어서 마지막 수단입니다.

`usb_max_current_enable` 설정은 전원이 정말 5A를 낼 수 있을 때만 켜세요. 켜고 나서 전원이 못 버티면 오히려 더 불안정해집니다.

## 5V 3A일 때 라즈5가 하는 일

- 라즈5는 전원에 5V 5A를 요청합니다. 3A 전원이면 **USB 포트 전체 전류만 600mA로 제한**하고, 부팅할 때 "5A 전원이 아님" 경고를 한 번 띄웁니다.
- **CPU 속도와는 관계없습니다.** USB 장치가 없으니 실질적인 영향도 없습니다.
- 라즈5가 최대 부하로 돌아도 보통 약 7–8W(5V에서 약 1.5A)이고, 카메라를 더해도 3A(15W) 안에 여유 있게 들어갑니다. 이 수치는 일반적으로 알려진 값이고, 우리 영상 처리 부하로 직접 재 본 것은 아닙니다.

## CPU가 실제로 느려지는 경우는 두 가지뿐입니다

| 원인 | 조건 | 우리 로봇에서 |
|---|---|---|
| **전압 저하** | 라즈 입력이 약 4.6–4.75V 아래로 떨어짐 | 3A인지 5A인지와는 무관합니다. 모터가 출발하거나 구속될 때 순간 강하만 조심하면 됩니다 (앞에서 말한 콘덴서와 배선 대책) |
| **발열** | 칩 온도가 약 80°C를 넘으면 속도를 낮춤 | **이쪽이 더 현실적인 위험입니다.** 50Hz로 영상 처리를 계속 돌리면 열이 많이 나고, 기체 안쪽은 바람이 안 통합니다 |

그래서 **라즈5에 방열판이나 액티브 쿨러(작은 팬)를 꼭 다는 것**을 추천합니다. 경기 한 판은 짧지만, 대기와 시험 중에 계속 켜 두면 온도가 올라갑니다. 카메라 마운트와 컬러타워 마운트 근처에 공기가 통할 틈이 있는지도 봐 주세요.

## 확인 명령 (라즈에서, 영상 처리를 돌리고 모터를 구동한 뒤)

```bash

```

`0x0`이면 정상입니다. 0이 아니면 전압 저하나 발열로 느려진 적이 있다는 뜻입니다.

```bash
vcgencmd measure_temp
```

영상 처리를 몇 분 돌린 뒤 70°C 아래면 안전하고, 80°C에 가까우면 쿨러가 필요합니다.


3. **자이로 보정 (상보 필터):** 짧은 순간은 자이로를 적분하고, 길게는 가속도 각도로 천천히 보정합니다. 리프트 턴처럼 빠르게 기울어지는 동작에 필요합니다.

## 설계 파일에서 확인한 것

- **회로도 연결은 정상입니다.**
  - SDA(GPIO11)와 SCL(GPIO12)에 10k 풀업(R16, R15)이 `+3.3V`로 연결되어 있습니다.
  - 두 선에 연결된 부품은 TCA9548A(U4), MPU6050(U5), I2C_AUX 커넥터(J21)뿐입니다.
- **PCB에 단락은 없습니다.** DRC 결과 서로 다른 선끼리 붙은 곳(쇼트)이나 간격 위반은 0건입니다.
- **풀업 전원은 보드의 레귤레이터에서만 나옵니다.** 이게 가장 중요한 점입니다.
  - `+3.3V`는 AMS1117(U3) 하나가 만듭니다. U3의 입력은 `+5V`입니다.
  - ESP32 보드 자체의 3V3 핀(1, 2번)은 어디에도 연결되어 있지 않습니다.
  - 그래서 ESP32가 켜져 있어도 U3가 3.3V를 못 내면 풀업 전원이 0V입니다.
  - 그 상태에서 MPU6050은 전원 없이 신호선에만 연결되고, 칩 내부 보호 다이오드가 SDA·SCL을 거의 0V로 끌어내립니다.
  - "어떤 방식으로 해도 둘 다 LOW이고, 칩(MUX)을 빼도 그대로"라는 증상과 정확히 맞습니다.

## 가능성 순위

1. **`+3.3V`가 없음:** U3 미장착, 냉납, 불량, 또는 `+5V` 입력이 없음.
   - 예를 들어 ESP32 USB만 꽂고 메인 전원(U1)을 안 켠 상태가 해당될 수 있습니다.
   - 이때 IR, 컬러센서 커넥터의 3.3V도 같이 죽어 있을 것입니다.
2. **MPU6050이 SDA·SCL을 잡고 있음:** 모듈 불량, 방향을 뒤집어 꽂음, 핀이 한 칸 밀림.
   - MUX를 빼도 MPU6050은 여전히 같은 선에 붙어 있습니다.
3. **납땜 단락:** R15/R16(0603) 패드, U5 핀, J21 쪽.
4. **XL4015(U2) 모듈과의 접촉:** PCB에서 U2 영역이 ESP32 헤더 17(SDA), 18(SCL)번 핀 위에 겹쳐 있습니다.

   - 다만 다른 핀도 수십 개 같은 영역에 있으므로 하나만 의심할 근거는 약합니다.
5. **펌웨어:** 가능성이 낮습니다. `Wire.begin(11, 12)`만 쓰고, 두 핀을 LOW로 출력하는 코드는 없습니다.

EN과 IS의 위치만 서로 반대입니다. 두 케이블을 같은 모양으로 만들었다면 이렇게 됩니다.

- 왼쪽은 드라이버의 EN 핀이 IS 분압 저항(470Ω에서 GND)에 연결됩니다. EN이 계속 LOW라서 드라이버가 꺼진 상태로 있습니다.
- 대신 드라이버의 IS 출력이 ESP32의 EN_1(GPIO40)에 연결됩니다.

드라이버를 바꿔도, 단순 출력 코드로 돌려도 왼쪽만 안 도는 증상과 맞습니다. 앞에서 소손으로 생각했던 왼쪽 드라이버도 실제로는 멀쩡했을 수 있습니다.

## 먼저 측정 (지금 `raw_motor_v2` 상태, 바퀴 띄우고)

기판 쪽 J9 핀을 GND 기준으로 잽니다. 오른쪽 J10과 비교하면 됩니다.

| J9 핀 | 정상값 |
|---|---|
| 6, 7 (EN_1) | 약 3.3V |
| 5 (R_PWM_1) | 약 0.6–0.7V (멀티미터에는 20% 듀티의 평균으로 보임) |
| 4 (L_PWM_1) | 0V |
| 1 (+5V) | 5V |

결과에 따라 다음과 같이 판단합니다.

- **하나라도 값이 다르면** 기판이나 ESP32 출력 쪽 문제입니다. 케이블을 바꿔도 해결되지 않습니다.
  - 예를 들어 EN_1이 0V이면 GPIO40을 의심합니다.
  - R_PWM_1이 0V이면 GPIO41이나 그 배선을 의심합니다.
- **전부 정상이면** 같은 값을 드라이버 모듈 핀에서 다시 잽니다. 기판에서는 정상인데 모듈에서 다르면 케이블 문제입니다.
- **모듈 핀까지 정상이면** 드라이버 출력 단자(모터 쪽)의 전압을 잽니다. 배터리 전압의 20% 정도가 나와야 합니다.
  - 전압이 나오는데 안 돌면 모터나 모터 선 문제입니다.
  - 전압이 안 나오면 드라이버 전원(B+, B-) 쪽 문제입니다.
