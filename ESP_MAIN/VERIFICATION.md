# V1 펌웨어 요구사항·구조·검증 기록

검토일: 2026-10-05. 대상: `D:\C_ROBOT\ESP_MAIN`의 실제 소스.
하드웨어가 없는 상태에서 코드 수정, PC 자동 검증, ESP32 빌드를 실시했다.
아래의 통과는 시험한 입력과 조건에서의 결과이며 모든 하드웨어 동작을 보증한다는 뜻은 아니다.

## 최신 통합 검토 — 생산/벤치/영상 처리

2026-10-05 전체 펌웨어 연결부와 별도 센서·벤치 진입점을 재검토했다. 아래 결과를 과거 수치보다 우선한다.

- `requestStop()` 전에 누르기 시작한 SW2를 나중에 놓으면 재출발할 수 있었다.
  안정된 눌림과 아직 디바운스 중인 눌림 모두 시험으로 재현했다. 정지/집계 고장/교정 진입 시
  기존 제스처를 취소하며, 눌린 버튼은 안정된 해제 후 새 눌림·해제를 해야 한다.
- 생산 ZoneEscape가 최초 위험 비트만 사용해 새 후방 위험에도 후진했다. 시험으로 재현하고
  진행 방향의 새 위험은 한 번 브레이크 후 새 방향으로 판단하도록 수정했다. 전후방 동시 위험은
  브레이크를 유지한다. 회전 단계는 현재 확인된 위험 방향을 사용한다. 벤치도 회전 방향을 갱신한다.
- `CAL MARGIN`의 `%u` 입력이 뒤쪽 쓰레기 문자열이나 큰 정수의 넘침을 받아들일 수 있었다.
  잘못된 입력으로 교정 허용 범위가 바뀌는 시험을 재현했다. 이제 두 개의 1..100 정수만 허용한다.
- 잘못된 공개 벤치 모드 값은 STOP으로 정규화한다. 모터 API의 `timeoutMs > INT32_MAX`는
  시간 순환 비교가 불가능하므로 InvalidArgument와 브레이크로 거부한다.
- 일반 영상 추적 실행에서 FPS 목록이 계속 늘어나던 부분은 최근 60프레임만 보관하도록 했다.
  명시적 벤치마크의 전체 측정 목록은 보고서 생성을 위해 유지한다.

## 1. 이번 작업의 기준

### 후속 센서 최적화 (2026-10-05)

AS7341은 이전 두 뱅크 방식 대신 F2/F3/F5/F6/F7/Clear 단일 묶음 연속 측정으로 변경했다.
기본 노출 5000us 요청(4998.44us 실제 설정), X16, 센서별 LED 20mA이며 실측 전 시작값이다.
완료 이벤트 AINT(APERS=0, SP_IEN)와 최소 수광 간격으로 새 샘플을 구분한다.
ASTATUS부터 버스트 읽기로 래치/포화를 검사한다. 초기 SMUX 이후 수광을 끄지 않는다.
모의 시험에 완료 이벤트 write-one-to-clear, 연속 측정, 단일 묶음 채널 매핑,
동일 시각 중복 읽기, 포화 해제 후 유효 측정을 추가했다. 검증 결과는 아래 기존 기록보다
이 후속 변경의 결과를 우선한다. 광학 성능/실제 최대 지연은 미검증이며 상세 조건은 README에 있다.

후속 검증: AS7341 12그룹/4,981회, TCS34725 12그룹/4,542회 PC 검사 통과.
생산/센서 전용 × AS7341/TCS34725 네 PlatformIO 환경 모두 빌드 성공.

- V1 핀 배치를 유지한다. PCBV2 핀 배치는 적용하지 않는다.
- 바닥 센서는 컬러 센서 네 개뿐이다. IR, IMU, 전류, 엔코더, 배터리 ADC를 추가하지 않는다.
- 센서 1/2/3/4는 전방 왼쪽/전방 오른쪽/후방 왼쪽/후방 오른쪽이다.
  모터 1은 왼쪽, 모터 2는 오른쪽이다.
- AS7341 또는 TCS34725 한 종류를 빌드 시 선택한다. 두 종류를 동시에 꽂는 구성은 아니다.
- 오류 복구 엔진을 만들지 않는다. 채널 오류는 한 번 기록하고 해당 채널을 제외한다.
- SW1 안전 정지와 모터 명령 만료는 단순 오류 출력보다 우선하는 필수 안전 기능이다.
- 공격 전략의 세부 최적화는 하지 않는다. 기존 시간 기반 공격을 유지하고 구조적 오류를 수정한다.

## 3. 실제 실행 흐름

```text
전원/리셋
  → 모터 핀 안전 LOW → UART 로그 열기 → PWM 초기화
  → 버튼 ISR → LED → 컬러 센서/NVS → 라즈 UART → 안전관리자
  → 시작 대기 (모터 브레이크)
       ├─ CAL START → 자세 안내 → READY → 카운트다운 3초 → 측정 3초
       │              → ACCEPT/RETRY/BACK → 48단계 완료 → CAL SAVE
       └─ SW2 정상 눌림·해제 → 운전 허용

운전 루프
  안전/버튼/모터 만료 확인
    → 라즈 패킷 읽기 → 컬러 센서의 짧은 I2C 단계 → 안전 다시 확인
    → FSM 판단 → 좌우 명령 변환 → 출력 제한/PWM 적용
    → LED → 제한된 이벤트 로그 → 1ms 양보

FSM 기본 흐름
  탐색 → 서로 다른 목표 프레임 2회 확인 → 정렬/접근
       → 가까운 중앙 목표 → 돌진 220ms → 브레이크 90ms
       → 스포크 삽입 전진 350ms → 밀기
       → 목표 상실 시 마지막 새 목표 시각 기준 최대 500ms 밀기
       → 후진 260ms → 탐색

우선 처리
  SW1 → 모든 일반 실행 종료, 재부팅 필요
  신뢰 가능한 위험색 → 공격 어느 단계에서든 위험구역 회피
```

센서·FSM·통신은 읽기 쉬운 메인 루프에 그대로 있다.
모터 명령 만료만 작은 FreeRTOS 태스크에서 별도로 감시한다.
이는 메인에서 센서/I2C 처리 중이어도 만료된 구동을 정지시키기 위한 것이다.
감시 주기는 5ms이며 80/100ms에 정확히 일치하는 하드 실시간 정지를 보증하지는 않는다.

## 4. 현실적인 조합의 처리 정책

| 상황 | 처리 |
|---|---|
| 전원 인가, SW2 미조작 | 센서/통신은 읽지만 주행하지 않음 |
| 부팅부터 SW2 눌림 | 첫 해제로 출발하지 않음; 다시 눌렀다 놓아야 함 |
| 라즈가 아예 없음 | SW2 시작 후 탐색 가능 |
| 라즈가 재부팅·중단 | 짧은 목표 상실 처리 후 탐색; 시스템 시작 상태는 유지 |
| 라즈가 같은 sequence만 재전송 | 통신 생존과 영상 신선도를 구분; 영상은 120ms 뒤 오래된 것으로 판단 |
| 끊긴 라즈가 새 정상 패킷 전송 | 다음 정상 입력으로 사용; 재접속/재부팅 명령을 보내지는 않음 |
| 컬러 센서 하나/전체 초기화 실패 | 채널 오류와 Unknown; 부팅/시작은 계속 |
| 사용 중 센서 I2C/수광 타임아웃 | 해당 채널은 재부팅 전까지 제외; 자동 초기화·재시도 없음 |
| 무수광/포화 값 | 해당 측정만 무효; 동일한 오류는 반복 기록하지 않음 |
| 색이 바뀌었거나 무효 값 입력 | 이전 reliable 판정을 바로 취소; 새로운 같은 색 세 번 필요 |
| 교정 데이터 없음/형식·설정 불일치 | 임시 임계값 사용; 자동 교정하지 않음 |
| 교정 중 SW2 조작 | 교정 중단, 모터 계속 정지; 별도의 새 눌림·해제 필요 |
| 교정 NVS 저장/삭제 실패 | 오류 출력; 수동 명령만 허용, 기존 RAM 교정 데이터 보존 |
| 모터/애플리케이션 집계 고장 | 즉시 정지·운전 요청 폐기; 상태가 정상으로 보고되어도 자동 출발하지 않음 |
| 모터 명령 만료 | 브레이크, 다음 새 정상 명령이 없으면 계속 정지 |
| SW1 입력 | 구동 영구 금지; 스위치 해제/소프트웨어 해제 API로 복구 불가 |

라즈의 새 입력을 다시 사용하는 것과 범위 오류 이후 다음 정상 측정을 읽는 것은
일반 입력 처리다. 센서 리셋, 보드 재부팅, 재접속 루프 등의 자동 복구는 구현하지 않았다.

## 5. 발견해 수정한 주요 문제

1. 센서 라이브러리의 수광 대기/SMUX 대기로 제어 루프가 길게 정지할 수 있었다.
   짧은 Wire 레지스터 단계와 유한 타임아웃으로 바꾸었다. 수광 시간만큼 delay하지 않는다.
2. 목표가 오른쪽일 때 전진 조향 부호가 반대였다. 오른쪽 조향은 왼쪽 모터가 더 빠르도록 통일했다.
3. 브레이크 전환 시 이전 PWM 상태에서 EN부터 올리는 순간 구동 위험이 있었다.
   EN 차단 → 브레이크 PWM → EN 설정 순서로 바꾸었다.
4. ESTOP 정지 루프의 반복 EN LOW가 브레이크를 취소할 수 있었다.
   ISR의 즉시 차단 이후에는 선택한 전기적 브레이크 조합을 유지한다.
5. ESTOP 브레이크 중 공용 드라이버 호출이 PWM을 먼저 바꿀 수 있었다.
   구동 금지 확인을 출력 전/EN 직전에 적용했다. 실제 SW1 래치는 해제할 수 없다.
6. 모터 만료 감시가 메인 루프에만 의존했다. 작은 별도 만료 감시를 추가했다.
   시간 카운터 순환 시 기한 0도 실제 기한으로 처리한다.
7. 안전 고장 보고 후 motorAllowed가 한 루프 동안 이전 값일 수 있었다.
   보고 시점에 안전 상태를 갱신하고 기존 출발 요청을 폐기한다.
8. 버튼 해제의 짧은 재채터링이 디바운스 시간을 단축할 수 있었다.
   새 에지가 들어오면 안정화 시간을 다시 센다.
9. UART 중간 바이트 유실 시 다음 헤더를 버리거나 라즈 재부팅 sequence를 거부할 수 있었다.
   후보 헤더 꼬리를 보존하고 끊김 이후 첫 정상 패킷은 새 sequence 기준으로 받는다.
10. 목표 유효 시간을 현재 루프 시각으로 계속 늘릴 수 있었다.
    실제 새 영상 시각을 기준으로 목표 상실 시간을 계산한다.
11. 캘리브레이션 긴 입력 뒤 남은 문자열이 명령이 될 수 있었다.
    손상/너무 긴 입력은 줄 끝까지 버린다. 저장 길이·유한값·설정 호환도 검사한다.
12. 캘리브레이션 구조체 초기화에 약 4.6KB 스택 임시값이 생겼다.
    작은 참조 단위로 초기화해 해당 컴파일 경고를 없앴다.
13. 빨강/노랑 임시 판정 범위가 겹쳐 빨강이 노랑으로 먼저 판정될 수 있었다.
    우세 빨강을 먼저 검사하고 모든 색의 예제를 시험했다.
14. I2C 전송 후 새 샘플 시각이 이전 루프 시각보다 늦어 unsigned 나이 계산이 잘못될 수 있었다.
    전송 후의 시각으로 샘플 신선도를 검사한다.
15. AS7341 ADC 값을 데이터 래치 없이 읽을 수 있었다.
    ASTATUS부터 연속 읽고 아날로그/디지털 포화 상태를 함께 처리한다.
16. 로그 송신 공간의 고정 최소치만 확인해서 긴 로그가 UART 쓰기를 기다릴 수 있었다.
    실제 한 줄 전체 길이를 확인한 뒤 쓰고, 공간이 없으면 다음 루프로 미룬다.
17. LED TTL이 millis 순환 시 0이면 영구 요청으로 바뀔 수 있었다.
    만료 여부와 만료 시각을 분리했다. 실제 FSM 상태가 바뀔 때만 LED 요청한다.

## 6. 재현 가능한 하드웨어 없는 검증

작업 폴더의 PowerShell에서:

```powershell
cd D:\C_ROBOT\ESP_MAIN
.\tests\run_host_tests.ps1
```

실제 생산 소스와 `setup()/loop()`를 PC용 가짜 GPIO/UART/I2C/NVS에 연결한다.
FSM/안전/판정 알고리즘을 별도의 가짜 구현으로 바꾸지 않는다.
AS7341과 TCS34725를 각각 컴파일하고 12개 시험 그룹을 실행한다.
네이티브 g++가 필요하며 PATH 또는 PlatformIO의 toolchain-gccmingw32를 사용한다.
시험 파일은 생산 빌드에 들어가지 않는다. 출력 실행 파일은 `.pio/host-tests`에 둔다.

검증 그룹:

- 모터 제한·조향·100ms 만료·시간 순환
- 버튼 채터링·부팅 눌림·출력 변경 중 SW1 인터럽트
- 시작·고장 즉시 금지·수동 재시작·교정 금지
- UART 중복/손상/바이트 유실/라즈 재부팅/sequence 순환/무작위 바이트 5만 개
- FSM 공격 시각 경계·공격 각 단계의 위험색 우선 처리·네 모서리 회피·목표 상실
- 센서 정상/미연결/포화/변환 정지/SMUX 정지/자동 재초기화 금지
- 새 색 측정 세 번과 색 변경 시 기존 판정 취소
- 실제 48단계 교정, 서로 다른 자세 밝기, RETRY/BACK, 저장·삭제 실패, NVS 손상
- 로그 송신 공간 부족과 LED 우선순위/만료/시간 순환
- 실제 메인 루프의 시작·교정 중단·라즈 없는 탐색
- I2C 거래마다 시간이 흐르는 조건, 전체 센서 누락 부팅, 모터 초기화 실패, 부팅 SW1

공격 상태가 변하는 간단한 출력 데모:

```powershell
.\tests\run_host_tests.ps1 -Demo
```

이는 가상 시각과 가상 입력을 이용한 흐름 시연이다. 실제 차량/영상/물리 시뮬레이터는 아니다.

ESP32용 네 가지 빌드:

```powershell
pio run -e yd_esp32_s3 -e yd_esp32_s3_tcs34725 -e sensor_serial_test -e sensor_serial_test_tcs34725
```

검토 중에는 기존 산출물 잠금을 피하려고 `PLATFORMIO_BUILD_DIR=.pio\build_review`를 사용했다.
센서 단일 묶음 최적화 이전의 실행 기록 (최신 결과는 문서 상단):

| 검증 | 결과 |
|---|---|
| AS7341 PC 시험 | 11개 그룹, assert 검사 4,845회 통과 |
| TCS34725 PC 시험 | 11개 그룹, assert 검사 4,542회 통과 |
| ESP32 네 환경 | 모두 빌드 성공, 프로젝트 소스 경고 없음 |
| Cppcheck warning/performance/portability | 소스 19개 파일 통과 |
| 생산 AS7341 메모리 | RAM 36,188 bytes / Flash 368,853 bytes |
| 생산 TCS34725 메모리 | RAM 36,188 bytes / Flash 368,381 bytes |

assert 횟수에는 반복 측정 시 시간 비블로킹 확인 등이 포함된다.
9천여 개의 서로 다른 시나리오라는 뜻은 아니다.
최종 수치와 통과 결과는 테스트 출력 및 빌드 출력이 원본이다.

## 7. 실물에서 반드시 확인할 부분

코드 시험만으로 아래 항목을 확정할 수 없다.

1. 실제 보드의 플래시 용량과 업로드 설정. 현재 8MB DevKitC 설정이며 PSRAM은 사용하지 않는다.
2. BTS7960 실제 EN/PWM 배선과 브레이크 효과. 현재 BothPwmLowEnableHigh이며 실측 검증 전이다.
   전원 리셋 중의 하이임피던스와 드라이버 풀다운도 소프트웨어만으로 보장할 수 없다.
3. 좌/우 모터 정방향. 방향 반대이면 motor_config.hpp의 LEFT/RIGHT_MOTOR_INVERTED를 바꾼다.
4. 센서 모듈의 보조 조명과 실제 TCA 채널 순서, 배선 길이·I2C 풀업·버스 품질.
5. 실제 경기장 색과 높이별 판정. 임시 임계값은 미교정 출발용 초기값이지 검증된 경기용 값이 아니다.
   V1에는 IMU/거리센서가 없으므로 상대 로봇 표면/공중/검정 바닥을 항상 구분할 수는 없다.
6. 실제 수광 주기와 3회 확인 지연. 100Hz는 목표이며 현재 달성했다고 주장하지 않는다.
   현재 AS7341은 전체 스펙트럼 대신 단일 묶음 약 5ms 연속 수광이다.
   내부 보정/I2C/스케줄링/누락된 샘플/단차 경계의 혼합색 때문에 20ms/10mm를 최대값으로 보장하지 않는다.
   TCS34725를 614ms 수광으로 바꾸면 3초당 최소 5샘플 교정 조건을 못 채울 수 있어 측정 시간도 조정한다.
7. ESP32의 실제 ISR/FreeRTOS 동시 실행과 만료 지연. PC 테스트는 결정적인 인터럽트 타이밍을 모델링할 뿐이다.
8. 라즈 실제 송신과 종단간 UART. CRC가 없으므로 형식상 정상인 비트 손상까지 모두 검출하지는 못한다.
9. 급정거·스포크 기동과 출력 65%의 실제 기체 안정성. 시간 기반 제어일 뿐 접촉/삽입 성공을 측정하지 않는다.

빠른 첫 시연 순서:

1. 모터 전원을 분리하고 센서 전용 테스트 환경으로 UART0 115200에서 네 센서 순서를 확인한다.
2. 출력 상한을 먼저 낮추고 바퀴를 띄워 생산 환경으로 업로드한다. UART0는 57600이다.
3. 전원 직후 무구동 → SW2 눌림·해제 → 좌우 방향 → SW1 즉시 차단/브레이크 유지/ESTOP만 출력 확인.
4. SW1을 놓아도 출발하지 않고 재부팅해야 하는지 확인한다.
5. 라즈 없이 탐색 → 라즈 정상 송신 → 분리/재부팅 시 탐색 전환을 확인한다.
6. 바닥에서 돌진하기 전에 실제 색/높이 교정과 위험색 회피부터 낮은 출력으로 확인한다.

## 8. 레지스터 확인 근거

AS7341의 ADC 래치, 포화, 초기화 대기, 수광 시간은 제조사
[AS7341 DS000504](https://look.ams-osram.com/m/24266a3e584de4db/original/AS7341-DS000504.pdf)의
32~33, 47, 49쪽을 대조했다. SMUX 연결 값은
[Adafruit AS7341 라이브러리](https://github.com/adafruit/Adafruit_AS7341/blob/master/Adafruit_AS7341.cpp)의
F1~F4/F5~F8 연결 정의와 대조했다. 자료 대조는 실제 센서 실험을 대신하지 않는다.
