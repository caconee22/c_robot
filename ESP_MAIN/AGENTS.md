# ESP_MAIN 작업 지침

이 문서는 다른 AI나 개발자가 `ESP_MAIN` 펌웨어 작업을 이어갈 때 먼저 읽어야 하는 프로젝트 기준 문서다.
사용자가 확정한 내용과 아직 확인되지 않은 가정을 구분해서 기록한다.

## 대화 및 작업 원칙

- 사용자가 영어로 질문하더라도 항상 한국어로 답한다.
- 펌웨어는 PlatformIO 기반 ESP32-S3 Arduino 스타일로 작성한다.
- 큰 기능은 센서 처리부, 통신부, 모터 제어부로 분리한다.
- 안전스위치 처리는 다른 모든 동작보다 우선한다.
- 코드는 짧고 이해하기 쉽게 유지한다. 오류는 종류와 채널을 기록하고 끝낸다.
  자동 재부팅, 센서 재초기화, 반복 재접속, 범용 복구 프레임워크는 추가하지 않는다.
- 현재 요구사항별 구현과 검증 범위는 `VERIFICATION.md`를 함께 읽는다.
- 사용자가 명시적으로 요청하기 전에는 커밋이나 푸시를 하지 않는다.
- 하드웨어에서 확인되지 않은 전기적 동작을 임의로 확정하지 말고, 가정임을 표시한 뒤 실험으로 확인한다.

## 로봇 개요

- 용도: 2026 IRC 씨름 로봇 대회용 자율주행 로봇
- 메인 제어기: YD-ESP32-S3
- 주행: BTS7960 모터 드라이버 2개로 좌우 모터 제어
- 색상 감지: AS7341 또는 TCS34725 컬러 센서 4개 중 한 종류를 빌드 시 선택
- I2C 확장: TCA9548A 멀티플렉서
- V1 펌웨어에는 IR, 거리센서, IMU, 전류센서, 엔코더, 배터리 ADC를 사용하지 않는다.
- 바닥 색은 네 모서리 컬러 센서만으로 판별한다.
- 영상 처리: 전방 카메라 영상을 라즈베리파이에서 처리하고 결과 좌표만 ESP32로 전달한다.
- 상태 표시: 내장 GPIO48 및 외부 GPIO13의 WS2812 각 1개

## 확정 핀맵

### 컬러 센서 위치

기체 전방을 위로 보았을 때 1번은 전방 왼쪽, 2번은 전방 오른쪽,
3번은 후방 왼쪽, 4번은 후방 오른쪽이다. 기본 TCA9548A 채널은 순서대로
0, 1, 2, 3이며 실제 배선 확인 전까지는 가정값이다.

### 스위치

| 신호 | ESP32-S3 GPIO | 기능 |
|---|---:|---|
| SW1 | GPIO15 | 안전/긴급정지 스위치 |
| SW2 | GPIO16 | 로봇 작동 스위치 |

- 두 스위치는 `INPUT_PULLUP`을 사용한다.
- GND로 연결되는 능동 LOW 입력으로 처리한다.
- 스위치 채터링을 소프트웨어로 디바운스한다.
- SW1은 FALLING 인터럽트에서 즉시 비상정지를 래치하고 BTS7960의 EN 네 개를
  LOW로 만든다. 한 번 래치되면 스위치를 놓아도 복구하지 않으며 재부팅해야 한다.
- 비상정지 후 일반 실행은 영구 정지 루프에 들어가고 UART0에는 `ESTOP`만 3초마다
  출력한다.
- ISR에서는 EN을 차단하고, 일반 실행 문맥에서 PWM을 브레이크 조합으로 바꾼 뒤
  브레이크를 유지한다. 영구 정지 루프에서 EN을 계속 LOW로 덮어쓰지 않는다.
- SW2는 푸시버튼이다. 40ms 이상 안정된 눌림 다음에 40ms 이상 안정된 해제가
  확인되는 순간 시작 이벤트를 한 번 발생시킨다. 채터링 에지는 이벤트로 세지 않는다.

### 통신 및 I2C

| 신호 | ESP32-S3 GPIO | 용도 |
|---|---:|---|
| UART0 TX | GPIO43 | COM, SiK 텔레메트리, 디버그 출력 공유 |
| UART0 RX | GPIO44 | COM, SiK 텔레메트리 공유 |
| UART1 TX | GPIO17 | 라즈베리파이 통신 |
| UART1 RX | GPIO18 | 라즈베리파이 통신 |
| I2C SDA | GPIO11 | TCA9548A 및 AS7341 |
| I2C SCL | GPIO12 | TCA9548A 및 AS7341 |

- UART0에는 COM과 SiK 텔레메트리가 함께 연결되어 있으며 57,600bps 이벤트 로그 전용 출력으로 사용한다.
- UART0의 여러 장치가 동시에 ESP32 RX를 구동하면 충돌할 수 있으므로 수신 프로토콜을 추가할 때 주의한다.
- UART1은 라즈베리파이 전용이며 115,200bps로 사용한다.
- 라즈베리파이는 50Hz 고정 주기로 영상처리 결과를 일방적으로 전송한다.
- 추후 USB 통신도 고려한다.
- 라즈베리파이-ESP32 고정 배선은 신뢰도가 충분하다는 사용자 판단에 따라 UART 패킷에 CRC를 넣지 않는다.

### 네오픽셀

| 신호 | ESP32-S3 GPIO | 용도 |
|---|---:|---|
| Internal RGB | GPIO48 | 보드 내장 WS2812 1개 |
| External RGB | GPIO13 | 외부 WS2812 1개 |

두 LED는 `StatusLed`에서 독립 또는 동시 지정한다. LED 출력은 20ms 주기의 낮은
우선순위 `update()`에서만 실행한다. 호출 주체별 요청을 보존하고 상태 우선순위가
높은 요청을 표시한다. 같은 우선순위에서는 가장 최근 요청을 사용하며, 높은 요청이
해제되거나 TTL이 끝나면 이전의 낮은 요청이 자동으로 다시 표시된다.

| 상태 | 표시 | 우선순위 |

| EmergencyStop | 빨강 고정 | 255 |
| Fault | 빨강/흰색 빠른 교대 | 240 |
| MotorFault | 빨강/주황 빠른 교대 | 230 |
| SensorFault | 노랑 점멸 | 220 |
| ZoneEscape | 주황 빠른 점멸 | 200 |
| WallEscape | 자홍 빠른 점멸 | 190 |
| CommunicationLost | 보라 점멸 | 180 |
| Charging | 흰색 매우 빠른 점멸 | 150 |
| Pushing | 파랑 고정 | 140 |
| Aligning | 노랑 고정 | 130 |
| Tracking | 초록 고정 | 120 |
| Approaching | 청록 고정 | 110 |
| Searching | 빨강 점멸 | 100 |
| Ready | 파랑 고정 | 70 |
| WaitingForStart | 주황 점멸 | 50 |
| Booting | 파랑 점멸 | 40 |
| Off | 꺼짐 | 0 |

## 안전 및 모터 요구사항

- SW1 안전스위치가 동작하면 모터는 즉시 정지하고 비상 상태를 영구 래치한다.
- SW1을 해제해도 복구되지 않으며 다시 동작하려면 ESP32를 재부팅해야 한다.
- 최종 요구사항은 안전스위치 동작 시 BTS7960을 브레이크 상태로 만드는 것이다.
- 정확한 BTS7960 브레이크 입력 조합은 아직 모른다. 실제 모듈과 모터로 시험한 뒤 확정한다.
- 브레이크 방식이 확인되기 전 테스트 코드에서는 PWM과 EN을 모두 LOW로 내려 출력 차단/코스트 정지를 사용한다.
- 모터 테스트는 낮은 출력으로 모터별 3초씩만 구동한다.
- 실물 시험은 먼저 바퀴를 바닥에서 띄우고 진행한다.

## 카메라 및 라즈베리파이 통신 요구사항

- 카메라는 로봇 전방을 향하며 중앙 부근에서 약간 아래쪽을 본다.
- 라즈베리파이가 컬러 타워를 영상에서 검출한다.
- ESP32에는 영상 전체가 아니라 카메라 프레임 안 타워 좌표를 UART1으로 전달한다.
- 사용자가 최초 설명에서 해상도/프레임을 `19220*1080, 50F`로 적었다. 의도는 `1920x1080, 50 FPS`로 추정되지만 구현 전 확인이 필요하다.
- UART1 속도는 115,200bps로 확정되었다.
- UART 좌표 패킷은 14바이트 고정 길이, 리틀 엔디언 형식으로 확정했다.
- CRC는 사용하지 않는다.

### 라즈베리파이 영상 패킷 V1

라즈베리파이는 새 영상 프레임을 처리할 때마다 `sequence`를 1 증가시키며
`255 -> 0` 순환을 허용한다. 같은 처리 결과를 재전송할 때는 sequence를 증가시키지
않는다. 목표가 없어도 카메라와 처리 파이프라인이 정상이라면 50Hz로 계속 패킷을
보낸다.

| 바이트 | 크기 | 내용 |
|---:|---:|---|
| 0 | 1 | 헤더 `0xAA` |
| 1 | 1 | 헤더 `0x55` |
| 2 | 1 | 버전 `0x01` |
| 3 | 1 | 페이로드 길이 `0x0A` |
| 4 | 1 | sequence (`uint8_t`) |
| 5 | 1 | 상태 비트 |
| 6 | 2 | 중심 X (`uint16_t`, little-endian) |
| 8 | 2 | 중심 Y (`uint16_t`, little-endian) |
| 10 | 2 | 박스 폭 (`uint16_t`, little-endian) |
| 12 | 2 | 박스 높이 (`uint16_t`, little-endian) |

상태 비트는 bit0 `TARGET_VALID`, bit1 `TRACK_STABLE`, bit2
`MULTIPLE_TARGETS`, bit3 `BOX_CLIPPED`, bit4 `CAMERA_OK`, bit5
`PIPELINE_OK`이며 bit6~7은 0이어야 한다. 목표가 없으면 좌표와 박스 크기는 모두
0이고 bit0~3도 모두 0이어야 한다. 목표가 있으면 중심은 1920x1080 범위 안, 박스
크기는 1 이상이며 프레임 크기를 넘지 않아야 한다.

ESP32 파서는 블로킹 없이 헤더, 버전, 길이, 상태 조합, 좌표와 크기를 검사한다.
정상 패킷 수, 오류 수, 중복 sequence를 `RaspberryLink::status()`로 조회할 수 있다.
정상 패킷이 120ms 동안 없으면
`linkValid=false`, 새 sequence가 120ms 동안 없으면 `frameFresh=false`가 된다.
통신은 살아 있어도 같은 sequence만 반복되면 영상 처리 정지로 판단한다.

라즈베리파이는 주행 필수 장치가 아니다. 미연결, 재부팅, 통신 끊김은 예상된
상황이며 시스템 고장이나 모터 금지 조건으로 사용하지 않는다. 구동 FSM이
`VisionSnapshot::linkValid`와 `frameFresh`를 확인해 비전 없이 가능한 탐색 등 다른
주행 로직으로 전환한다.

## 컬러 센서 및 TCA9548A

- AS7341은 차량 네 모서리에 1개씩, 총 4개다.
- 기체 전방을 위로 보았을 때 센서 번호는 1번 전방 왼쪽, 2번 전방 오른쪽,
  3번 후방 왼쪽, 4번 후방 오른쪽으로 고정한다.
- 모터 1번은 차량 왼쪽 모터이고 모터 2번은 차량 오른쪽 모터다.
- 동일 I2C 주소 충돌을 피하기 위해 TCA9548A를 사용한다.
- 현재 센서 테스트 코드의 TCA9548A 주소는 기본값 `0x70`으로 가정한다.
- 현재 센서 테스트 코드의 AS7341 채널 순서는 TCA 채널 `0, 1, 2, 3`으로 가정한다.
- TCA 주소와 실제 채널 배치는 사용자가 아직 확정하지 않았으므로 배선 확인 후 수정한다.
- AS7341은 F2/F3/F5/F6/F7/Clear를 단일 묶음 연속 측정한다.
  센서 테스트도 이 여섯 채널만 출력하며 F1/F4/F8/NIR은 미측정이다.
- 생산 코드에서는 `include/sensors/sensor_config.hpp`의 `COLOR_SENSOR_MODEL` 한 줄로
  AS7341 또는 TCS34725를 선택한다. 두 센서는 동일한 TCA 채널과 모서리 순서를 쓴다.
- 같은 설정 파일에서 AS7341의 `AS7341_EXPOSURE_US`,
  `AS7341_GAIN`, `AS7341_LED_CURRENT_MA` 또는 TCS34725의
  `TCS34725_INTEGRATION`, `TCS34725_GAIN`을 조정한다. 이 값이 달라지면 기존
  캘리브레이션은 자동으로 무효 처리한다.
- 동일한 색이 `COLOR_CONFIRM_COUNT`회 연속 판정되어야 신뢰 가능한 색으로 공개한다.
  기본값은 3회다.
- 저장된 캘리브레이션이 없어도 하드코딩된 임시 임계값으로 부팅과 판정을 계속한다.
  센서 초기화 실패도 부팅을 막지 않으며 해당 센서만 `Unknown`으로 남긴다.
- `ColorSensorManager`가 TCA 선택, 센서 초기화, 라운드로빈 원시값 취득을 담당한다.
- 수광 완료를 기다리는 라이브러리 호출 대신 짧은 Wire 레지스터 단계로 진행한다.
  AS7341은 ASTATUS부터 연속 읽어 ADC 데이터를 래치하고 포화도 확인한다.
  AS7341은 한 묶음의 Clear로 비율을 정규화한다. APERS=0의 AINT 완료 이벤트를
  확인·소거하고 최소 수광 간격도 확인하며, AVALID만으로 새 샘플을 세지 않는다.
- I2C/수광 타임아웃 오류 채널은 재부팅 전까지 비활성화한다. 다른 채널은 계속 읽는다.
  무수광/포화는 해당 측정만 무효이며 재초기화하지 않고 다음 정상 측정을 진행한다.
- `FloorColorClassifier`와 `ColorCalibration`은 별도 파일로 유지한다.
- 기체에 추가 가림막/구조물을 설치할 수 없다. 자체 LED로 비추며 10mm 단차 때문에
  센서-바닥 간격은 3/10/20mm로 변한다. 고정 높이로 가정하지 않는다.
  근접 포화, 20mm 유색 바닥의 검정 오인, 경계 혼합을 고려하고 다음 작업에서도
  이 조건을 고려하고 있음을 사용자에게 설명한다. 상세 설정과 미검증 사항은 README를 읽는다.
- UART0에서 `CAL START`를 입력하면 시작 대기 상태에서만 48단계 안내식 교정을 시작한다.
  센서별로 빨강/노랑/파랑/검정과 평행10mm/들림20mm/눌림3mm를 각각 3초 측정한다.
- 캘리브레이션 명령은 `READY`, `ACCEPT`, `RETRY`, `BACK`, `STATUS`, `ABORT`,
  `CAL SAVE`, `CAL ERASE`, `CAL MARGIN <색비율%> <밝기%>`를 사용한다.
- 캘리브레이션 중 SW2가 눌리면 현재 시작 제스처를 폐기하고 측정을 중단한다.
  모터는 계속 정지하며 구동하려면 SW2를 다시 정상적으로 눌렀다가 놓아야 한다.

## 현재 소스 구조

생산용 코드는 `app`, `hardware`, `interrupts`, `motor`, `sensors`,
`communication`, `system`, `control` 모듈로 분리한다. 현재 V1의 부팅, 안전,
컬러 센서, 라즈 UART, FSM, 구동 변환, 모터 출력까지 연결되어 있다.

- `include/config.hpp`: UART 및 공통 주기 설정
- `include/motor/motor_config.hpp`: PWM 및 출력 제한 설정
- `include/sensors/sensor_config.hpp`: 센서 종류, 수광 시간, 게인, 판정 확인 횟수와 임시 임계값
- `include/control/control_config.hpp`: 탐색·정렬·접근·밀기·위험구역 회피 출력과 시간
- `src/app`: 부팅 순서
- `src/hardware`: 초기 안전 핀 상태와 리셋 원인 처리
- `src/interrupts`: SW1/SW2 ISR 이벤트
- `src/motor`: BTS7960 저수준 드라이버와 안전 출력 제어
- `src/sensors`: 센서 스냅샷 관리
- `src/communication`: 라즈베리파이 UART1 링크
- `src/system`: 안전관리, 이벤트로그, 상태 LED
- `src/control`: FSM과 구동 명령 변환 틀

PWM은 BTS7960 DC 모터에서 범용적으로 쓰기 좋은 20kHz/8비트로 확정했다.
주기는 50us이고 듀티 원시 범위는 0~255다. 생산용
`MotorController`의 출력 단위는 해상도와 무관한 -1000~+1000이다. 공격형 V1의
기본 런타임 출력 상한은 650(65%)이다. `setOutputLimit()`로 시험 결과에
따라 올릴 수 있지만 절대 상한 1000을 넘길 수 없다. 모터 명령은 기본 100ms 안에
갱신되지 않으면 워치독 정지한다. FSM 명령의 유효시간은 80ms다.
메인 루프 외에 작은 모터 만료 감시 태스크가 5ms 간격으로 확인한다.
전체 FSM/센서/통신을 여러 RTOS 태스크로 쪼개지는 않는다.
모터 모듈의 일반 래치 해제 API로도 SW1 영구 래치를 해제할 수 없으며 재부팅해야 한다.
급정거 시험을 위해 `BRAKE_STRATEGY`는 `BothPwmLowEnableHigh`로 선택했지만 실제
BTS7960 모듈에서 동적 브레이크가 맞는지 바퀴를 띄운 상태로 확인해야 한다.
센서 주기도 최종 확정하지 않았으며 두 센서의 수광 시간별 시험 후
설정한다. V1에는 ADC 센서가 없다. SW1/SW2는 인터럽트 이벤트를 사용하되 실제 디바운스와 상태 변경은
ISR 밖에서 처리한다.

### 모터 공용 API

- `MotorController::setTank(left, right, safety)`: 좌우 독립 명령
- `MotorController::setArcade(throttle, steering, safety)`: 속도/조향 명령
- `forward`, `reverse`, `rotateLeft`, `rotateRight`: 기본 주행 명령
- `stop`, `coast`, `brake`: 정지 명령
- `emergencyStop`, `clearEmergencyStop`: 래치형 비상정지
- `update`: 안전 상태 및 명령 만료 감시용 주기 호출
- `setOutputLimit`: 런타임 출력 상한 변경
- `status`: 요청값, 적용값, 드라이버 상태, 명령 결과 및 카운터 조회

`MotorController` 함수는 일반 태스크/메인 루프에서 공용으로 호출할 수 있도록
뮤텍스로 보호한다. ISR에서는 직접 호출하지 않는다. SW1 ISR은 비상정지를 가장 빨리
적용하기 위해 영구 구동 금지 래치와 BTS7960 EN 직접 차단만 수행한다.

### 상태 LED 공용 API

- `request(owner, target, state, ttlMs)`: 호출 주체·LED·상태·유효시간 지정
- `setInternal`, `setExternal`, `setBoth`: 대상별 간편 상태 지정
- `clear(owner, target)`: 해당 호출 주체의 요청 해제
- `setEmergencyStop`: 두 LED에 최상위 비상정지 표시
- `update(nowMs)`: 20ms 주기의 낮은 우선순위 물리 출력 갱신
- `state`, `status`, `stateName`, `priority`: 현재 표시 및 진단 조회

### 이벤트 로그 공용 API

UART0 57,600bps 로그는 고정 크기 32개 큐를 사용하며 `process()` 한 번에 최대
2개만 출력한다. 기본적으로 같은 이벤트 번호·소스·value1·문자열 조합은 1초에
한 번만 큐에 들어간다. 빠르게 변하는 측정값으로 중복 제한을 우회하지 않도록
`value2`는 반복 판정 키에서 제외한다. 상태, 모드, 오류는 전용 변경 감지 API를
사용해 값이 실제로 달라졌을 때만 한 번 기록한다.

이벤트 번호 범위는 다음과 같이 고정한다.

- 100번대: 부팅 및 시스템
- 200번대: FSM 상태, 작동 모드
- 300번대: 라즈베리파이 및 통신
- 400번대: 센서 오류
- 500번대: 모터 오류
- 600번대: 안전 및 비상정지
- 900번대: 사용자 정의 이벤트

주요 API는 다음과 같다.

- `log(EventId, value1, value2)`: 미리 정의된 번호로 기록
- `log(number, severity, source, value1, value2)`: 임의 번호로 기록
- `logText(...)`: 최대 39자의 수동 문자열을 복사해 기록
- `stateChanged`, `modeChanged`: 값 변경 시에만 이전값과 새 값을 기록
- `valueChanged`: 지정 값이 바뀔 때만 기록
- `faultChanged`: 소스·오류종류·세부채널별 발생/해제를 각각 한 번만 기록
- `process`: 낮은 우선순위 루프에서 UART 큐 출력
- `status`: 큐 수, 출력·드롭·중복 억제 횟수 조회. 큐 드롭은 별도 로그를 다시
  만들지 않고 이 상태 값으로만 확인한다.

일반 출력 형식은
`EV,시간ms,이벤트번호,심각도,소스,value1,value2[,문자열]`이다. ISR에서는
로거를 직접 호출하지 않고 플래그만 남긴 뒤 일반 태스크에서 호출한다. ESTOP에
들어가면 기존 큐를 폐기하고 이후 일반 로그를 거부하며 `ESTOP`만 3초마다 출력한다.

### 시스템 상태 관리자

`SystemManager`가 SW2 해제 이벤트를 단독으로 소비하고 모터 허용 여부를 결정한다.
다른 모듈은 버튼을 직접 운전 상태로 해석하지 않고 `SystemStatus` 또는
`SafetyStatus`를 조회한다. 안전 상태의 원본은 `SystemManager` 하나만 둔다.

상태 흐름은 다음과 같다.

- `Booting`: 초기화 직후
- `WaitingForStart`: SW2의 정상 눌림-해제를 기다림
- `Running`: 시작 요청과 필수 하드웨어 조건이 정상이며 모터 허용
- `SensorFault`: 센서 집계 상태가 비정상
- `MotorFault`: 모터 집계 상태가 비정상
- `SystemFault`: 애플리케이션 또는 기타 시스템 오류
- `EmergencyStop`: SW1 래치 후 재부팅 전까지 영구 정지

라즈 UART 패킷 파서는 시스템 상태 관리자와 분리되어 있다. 라즈 상태는
`RaspberryLink::latest()`로 구동 FSM에서만 판단한다. 라즈가 없거나 끊겨도
`SystemManager`의 상태와 모터 허용 여부는 바뀌지 않는다.

주요 API는 다음과 같다.

- `begin`, `update(nowMs)`: 초기화 및 안전 주기 처리
- `status`, `safetyStatus`, `state`, `running`, `motorAllowed`: 상태 조회
- `requestStop`: 소프트웨어 운전 종료 및 즉시 모터 정지
- `setSensorHealthy`, `setMotorHealthy`, `setApplicationHealthy`: 집계 건전성 보고

건전성이 `false`가 되면 즉시 모터 정지와 고장 상태 전환을 하고 시작 요청도 폐기한다.
건전성을 나중에 `true`로 보고하더라도 자동 재출발하지 않는다.
V1 컬러 센서의 개별 오류는 이 집계 고장에 연결하지 않고 해당 채널의 오류와 Unknown만 남긴다.
같은 오류 보고는 이벤트 로거가 중복 억제한다. SW2는 시작 기능만
하며 다시 누른다고 정지하지 않는다. 정지는 `requestStop()`으로만 요청한다.

### `include/pins.hpp`

- 전체 하드웨어 핀 정의 파일이다.
- 핀 번호 변경은 이 파일에서 우선 처리한다.

### `src/main.cpp`

- 안전 관리자와 모터 워치독을 가장 먼저 갱신한다.
- 라즈베리파이 패킷과 네 컬러 센서를 비블로킹 방식으로 갱신한다.
- 캘리브레이션 중에는 모터를 정지하고 FSM을 실행하지 않는다.
- 일반 운전에서는 `RobotFsm`이 센서와 비전으로 주행 의도를 만들고,
  `DriveLogic`이 좌우 모터 명령으로 변환해 `MotorController`에 전달한다.
- FSM 우선순위는 안전 정지, 색상 위험구역 회피, 목표 확인·정렬·접근,
  돌진·급정지·스포크 삽입·밀기, 비전이 없을 때 탐색 순서다.
- 공격 시퀀스가 시작되면 짧은 카메라 가림에는 중단하지 않는다. 돌진 220ms,
  급정지 90ms, 스포크 삽입 350ms 뒤 밀며, 목표를 잃어도 최대 500ms 계속 민다.
  이후에는 260ms 후진하고 다시 탐색한다.

### `src/sensor_serial_test.cpp`

- 모터 핀을 초기화하거나 변경하지 않는 별도 센서 점검 코드다.
- UART0 115200bps로 약 100ms마다 다음 값을 출력한다.
  - SW1, SW2 원시 입력 상태
  - 선택된 센서가 AS7341이면 4개의 F2/F3/F5/F6/F7/Clear 값과 sequence/age
  - 선택된 센서가 TCS34725이면 4개의 R, G, B, Clear 값
  - TCA 채널 선택 오류, 센서 초기화 오류, 센서 읽기 오류
- 모터 핀을 건드리지 않기 때문에 센서 시험 중에는 모터 전원을 분리하는 것이 안전하다.

## PlatformIO 환경

생산용 FSM 펌웨어 빌드:

```powershell
pio run -e yd_esp32_s3
```

센서 시리얼 점검 빌드:

```powershell
pio run -e sensor_serial_test
```

센서 시리얼 점검 업로드:

```powershell
pio run -e sensor_serial_test -t upload
```

UART0 시리얼 모니터:

```powershell
pio device monitor -b 57600
```

센서 전용 테스트 환경의 UART0 모니터는 기존대로 115,200bps를 사용한다.

현재 PlatformIO 보드는 범용 `esp32-s3-devkitc-1`로 설정되어 있다. 실제 YD-ESP32-S3의 플래시 및 PSRAM 용량은 아직 확인하지 않았으며, 해당 기능을 사용하기 전에 보드 옵션을 맞춰야 한다.

`yd_esp32_s3_tcs34725`, `sensor_serial_test_tcs34725` 환경은 설정 파일을 수정하지
않고 TCS34725 구성을 빌드하는 검증/업로드 선택지다. 기본 환경은 설정 파일의 한 줄을 따른다.
하드웨어 없는 실제 소스 자동 검증은 `tests/run_host_tests.ps1`로 실행한다.
이 검증은 전기적 브레이크나 실제 ESP32 스케줄링/센서 수광의 실물 검증이 아니다.

## 대회 규정에서 펌웨어에 직접 영향을 주는 내용

원본 규정 파일은 저장소 루트의 `2026년 IRC 씨름 로봇 규정-20260511.pdf`다.

- 로봇은 완전 자율주행이어야 하며 경기 중 리모컨을 사용할 수 없다.
- 카메라는 최대 2대다.
- 스위치는 ON/OFF 전원 인가 목적으로만 사용해야 하며 방향이나 전략을 선택하는 입력으로 쓰면 안 된다.
- 경기 시작 전에 로봇 전원이 들어와 있어도 되지만 구동장치가 움직이면 안 된다.
- 경기 시작 시 팀장은 구동 스위치만 조작할 수 있다.
- 안전스위치는 전략 입력이 아니라 안전 정지 기능으로만 사용한다.
- 경기장 바닥은 검은색이고 빨간색 중앙 홈, 파란색 모서리 홈, 노란색 직사각형 홈이 있다.
- 홈 깊이는 10mm이며 노란색 홈은 득점 구역이 아니지만 높이 차가 존재한다.
- 로봇이 홈에서 10초 안에 빠져나오지 못하거나 작동 불능이 되면 경기상 불이익이 있다.
