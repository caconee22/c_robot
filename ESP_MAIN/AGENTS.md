# ESP_MAIN 작업 지침

이 문서는 다른 AI나 개발자가 `ESP_MAIN` 펌웨어 작업을 이어갈 때 따라야 하는 **규칙**만 담는다.
구조 요약은 [MAP.md](MAP.md), 설명·사용법은 [README.md](README.md), 검증 이력은
[VERIFICATION.md](VERIFICATION.md)에 있다. 핀·패킷·설정 숫자는 코드가 원본이며 이 문서에 복사하지 않는다.
사용자가 확정한 내용과 아직 확인되지 않은 가정을 구분해서 기록한다.

## 대화 및 작업 원칙

- 사용자가 영어로 질문하더라도 항상 한국어로 답한다.
- 펌웨어는 PlatformIO 기반 ESP32-S3 Arduino 스타일로 작성한다.
- 큰 기능은 센서 처리부, 통신부, 모터 제어부로 분리한다.
- 안전스위치 처리는 다른 모든 동작보다 우선한다.
- 코드는 짧고 이해하기 쉽게 유지한다. 오류는 종류와 채널을 기록하고 끝낸다.
  자동 재부팅, 센서 재초기화, 반복 재접속, 범용 복구 프레임워크는 추가하지 않는다.
- 사용자가 명시적으로 요청하기 전에는 커밋이나 푸시를 하지 않는다.
- 하드웨어에서 확인되지 않은 전기적 동작을 임의로 확정하지 말고, 가정임을 표시한 뒤 실험으로 확인한다.
- 모듈을 추가·제거하면 해당 헤더의 `// Contract` 주석과 MAP.md 표를 함께 갱신한다.

## 하드웨어 기능 사용 금지 (V1·V2 공통)

사용자가 확정한 금지 사항이다. 편의, 디버깅, 성능 개선을 이유로도 예외를 두지 않는다.
AI가 아래 기능을 해결책으로 제안하거나 추가하지 않는다.

- **Wi-Fi 금지:** `WiFi.h`, ESP-NOW, OTA, 웹서버 등 Wi-Fi 무선을 켜는 코드와 라이브러리를 추가하지 않는다.
  V2는 ADC2 핀(GPIO13, 14, 19, 20)을 아날로그 측정에 쓰므로 Wi-Fi를 켜면 측정이 막힌다.
- **외부 플래시·PSRAM 금지:** PSRAM과 외장 플래시 확장 기능을 켜지 않는다
  (`BOARD_HAS_PSRAM`, `board_build.arduino.memory_type`, `board_build.psram_type` 등).
  저장이 필요하면 기존처럼 내장 플래시의 NVS만 쓴다.
  옥탈 PSRAM 모듈은 GPIO35~37이 모듈 내부에 연결돼 있어 설정만으로 해결되지 않을 수 있으니 모듈 표기를 확인한다.
- **USB 금지:** ESP32-S3 네이티브 USB(USB CDC, USB-JTAG, TinyUSB)를 쓰지 않는다.
  `ARDUINO_USB_CDC_ON_BOOT=0`을 유지하고 업로드·로그·콘솔은 UART0(GPIO43/44)로만 한다.
  V2는 USB 핀인 GPIO19/20을 모터 전류 측정에 쓴다.

## V2 하드웨어 준비 (브랜치 `v2/firmware-prep`)

V2 기판은 조립 중이며 V1 펌웨어와 핀이 다르다. V1 `pins.hpp`는 덮어쓰지 않고 버전별 핀맵과 빌드 환경으로 분리한다.
회로도에서 읽은 V2 핀은 사용자 확인 전까지 초안이다.

- 바닥 센서는 스펙트럼 센서 4개, TCA9548A 채널 0~3이다. 정확한 모델은 확인 중이다.
- IMU(MPU6050)는 I2C 메인 버스에 직접 연결된다. **상황 판단용 센서**이며 용도는 다음과 같다.
  - 상대 로봇과 힘겨루기 중인가 (구동 중인데 가속·이동이 거의 없음)
  - 들렸는가
  - 기울었는가
  - 벙커(홈) 안으로 빠졌는가
  - 벽을 밀고 있는가
  - 이동 중 가속 감지
  주행 자세 제어, 직진 보정 같은 폐루프 제어에는 쓰지 않는다. 판단 결과는 FSM 입력으로만 전달한다.
- BTS7960 전류 감지(IS) 핀을 쓸 수 있다. 용도는 **벽을 밀고 있는가**, **모터 스톨(구속)인가** 같은 상황 판단이다.
  IMU와 함께 써서 힘겨루기·벽 밀기·스톨을 구분한다. 전류 값으로 출력을 자동 제한하는 보호 기능은
  사용자가 요청할 때만 추가한다. 모터당 EN 핀은 하나(L_EN·R_EN 묶음)다.
- 엔코더 핀(GPIO36~39, 9, 10)은 기판에 있지만 **사용하지 않는다.** 초기화하지 않고 입력으로도 설정하지 않는다.
  추후 지원 가능성은 있으나 사용자가 요청하기 전에는 엔코더 기반 기능을 추가하거나 제안하지 않는다.
- IR 아날로그 입력 6개가 있다. 용도는 확인 중이다.
- 배터리 전압 분압 입력(×11)은 `BatteryMonitor`가 전원 투입 후 3초 동안만 쓴다. 셀 수 범위(기본 4S)를
  벗어나면 배터리 없음·잘못된 배터리로 보고 `SystemManager::setApplicationHealthy(false)`로 시작을 막는다.
  분압비와 기준 전압은 V2 실물에서 확인 전이다.
- V2 전용 기능은 별도 모듈로 만들고 V1 빌드에는 포함하지 않는다.

### V2 핀맵과 빌드

- 하드웨어 버전은 빌드 환경의 `-D HW_VERSION=2`로 고른다. 플래그가 없으면 V1이다.
  `include/pins.hpp`는 V1 핀을 그대로 두고 V2일 때만 `include/pins_v2.hpp`를 불러온다.
- V2 환경: `yd_esp32_s3_v2`, `robot_bench_v2`, `sensor_serial_test_v2`, `color_calibration_v2`.
  메모리 타입은 `qio_qspi`로 고정한다. PC 시험은 `tests/run_host_tests.ps1 -V2`.
- `pins.hpp`는 `BOARD_HAS_PSRAM`, 옥탈 PSRAM 메모리 타입, `ARDUINO_USB_CDC_ON_BOOT=1`이면 빌드를 멈춘다.
  이 검사를 지우거나 우회하지 않는다.
- V2는 모터당 EN이 하나라 `MOTOR*_LEN`과 `MOTOR*_REN`이 같은 핀을 가리킨다. SW1 ISR의 EN 차단 마스크는
  핀 상수에서 레지스터 뱅크를 계산하므로 핀을 바꿔도 ISR 코드는 손대지 않는다.
- V2에는 외부 WS2812가 없다(GPIO13은 IR6 입력). LED 상태 계산은 유지하고 물리 출력만 내장 LED로 한다.

### V2 오른쪽 모터 EN(GPIO35) 주의

- 모듈에 옥탈 PSRAM이 있으면 GPIO35~37은 모듈 내부 PSRAM에 연결돼 있다. PSRAM을 켜지 않으면
  쓸 수 있다는 Espressif 답변이 있지만 공식 문서는 권장하지 않는다.
- Arduino 코어 2.0.17의 `qio_qspi` 설정은 `CONFIG_SPIRAM=1`(쿼드)로 미리 빌드돼 있어 `setup()` 전에
  `psramInit()`을 항상 호출한다(`esp32-hal-misc.c`). 이때 PSRAM 칩이 GPIO35를 잠깐 구동할 수 있고
  펌웨어로는 막을 수 없다.
- V2 기판 첫 시험에서 모터 전원을 분리하고 다음을 확인한다.
  1. 전원 투입·리셋 순간 EN_2(GPIO35)가 HIGH로 튀지 않는다 (스코프, 로직 분석기 또는 LED).
  2. 부팅 로그에 PSRAM 초기화 성공 메시지가 없다.
  3. EN_2가 명령대로 켜지고 꺼지며, 반복해도 재부팅이 없다.
  4. SW1을 누르면 EN_1과 EN_2가 모두 즉시 LOW가 된다.
- 문제가 있으면 EN_2를 GPIO38 또는 GPIO39(쓰지 않는 왼쪽 엔코더 핀)로 점프하고 `pins_v2.hpp`의
  `MOTOR2_EN` 한 줄만 바꾼다. GPIO36·37은 같은 PSRAM 핀이라 쓰지 않는다. 기판 재제작도 선택지다.

## 로봇 개요

- 용도: 2026 IRC 씨름 로봇 대회용 자율주행 로봇
- 메인 제어기: YD-ESP32-S3
- 주행: BTS7960 모터 드라이버 2개로 좌우 모터 제어. 모터 1번은 왼쪽, 2번은 오른쪽이다.
- 색상 감지: AS7341 또는 TCS34725 컬러 센서 4개 중 한 종류를 빌드 시 선택
- I2C 확장: TCA9548A 멀티플렉서
- V1 펌웨어에는 IR, 거리센서, IMU, 전류센서, 엔코더, 배터리 ADC를 사용하지 않는다.
- 바닥 색은 네 모서리 컬러 센서만으로 판별한다.
- 영상 처리: 전방 카메라 영상을 라즈베리파이에서 처리하고 결과 좌표만 ESP32로 전달한다.
- 상태 표시: 내장 GPIO48 및 외부 GPIO13의 WS2812 각 1개. 상태별 색과 우선순위는 README §12.

## 핀과 배선

- 모든 GPIO의 원본은 `include/pins.hpp`다. V1 배선에 맞춰 확정된 값이며 변경하지 않는다.
- 센서 번호는 기체 전방을 위로 보았을 때 1번 전방 왼쪽, 2번 전방 오른쪽, 3번 후방 왼쪽,
  4번 후방 오른쪽으로 고정한다. 기본 TCA9548A 채널은 순서대로 0, 1, 2, 3이며 실제 배선 확인 전까지는 가정값이다.
- TCA9548A 주소는 기본값 `0x70`으로 가정한다. 사용자가 아직 확정하지 않았으므로 배선 확인 후 수정한다.
- SW1(안전/긴급정지)과 SW2(작동)는 `INPUT_PULLUP`, GND로 연결되는 능동 LOW 입력이다.
  채터링은 소프트웨어로 디바운스한다.
- UART0에는 COM과 SiK 텔레메트리가 함께 연결되어 있으며 57,600bps 이벤트 로그 전용 출력으로 사용한다.
  여러 장치가 동시에 ESP32 RX를 구동하면 충돌할 수 있으므로 수신 프로토콜을 추가할 때 주의한다.
- UART1은 라즈베리파이 전용이며 115,200bps로 사용한다. 추후 USB 통신도 고려한다.

## 스위치와 안전 규칙

- SW1은 FALLING 인터럽트에서 즉시 비상정지를 래치하고 BTS7960의 EN 네 개를
  LOW로 만든다. 한 번 래치되면 스위치를 놓아도 복구하지 않으며 재부팅해야 한다.
- 비상정지 후 일반 실행은 영구 정지 루프에 들어가고 UART0에는 `ESTOP`만 3초마다 출력한다.
- ISR에서는 EN을 차단하고, 일반 실행 문맥에서 PWM을 브레이크 조합으로 바꾼 뒤
  브레이크를 유지한다. 영구 정지 루프에서 EN을 계속 LOW로 덮어쓰지 않는다.
- SW2는 푸시버튼이다. 40ms 이상 안정된 눌림 다음에 40ms 이상 안정된 해제가
  확인되는 순간 시작 이벤트를 한 번 발생시킨다. 채터링 에지는 이벤트로 세지 않는다.
- SW1/SW2는 인터럽트 이벤트를 사용하되 실제 디바운스와 상태 변경은 ISR 밖에서 처리한다.
- ISR에서는 `MotorController`와 로거를 직접 호출하지 않는다. SW1 ISR은 영구 구동 금지 래치와
  BTS7960 EN 직접 차단만 수행한다.
- 모터 모듈의 일반 래치 해제 API로도 SW1 영구 래치를 해제할 수 없으며 재부팅해야 한다.

## 모터 요구사항

- SW1 안전스위치가 동작하면 모터는 즉시 정지하고 비상 상태를 영구 래치한다.
- 최종 요구사항은 안전스위치 동작 시 BTS7960을 브레이크 상태로 만드는 것이다.
- 정확한 BTS7960 브레이크 입력 조합은 아직 모른다. 실제 모듈과 모터로 시험한 뒤 확정한다.
  현재 생산/벤치의 브레이크 요청은 `motor_config.hpp`의 `BRAKE_STRATEGY`를 따른다.
  기본 BothPwmLowEnableHigh는 급정거 시험을 위해 선택했지만 실제 모듈에서 확인 전이다.
  동적 브레이크가 맞는지 바퀴를 띄운 상태로 확인한다. 코스트를 시험하려면 이 설정을 명시적으로 바꾼다.
- PWM은 20kHz/8비트로 확정했다. 출력 단위는 -1000~+1000이며 런타임 상한은 `setOutputLimit()`로
  올릴 수 있지만 절대 상한 1000을 넘길 수 없다. 기본값은 `motor_config.hpp`에 있다.
- 모터 명령은 기한 안에 갱신되지 않으면 정지한다. 메인 루프 외에 작은 모터 만료 감시 태스크가
  주기적으로 확인한다. 전체 FSM/센서/통신을 여러 RTOS 태스크로 쪼개지는 않는다.
- `MotorController` 함수는 뮤텍스로 보호되며 일반 태스크/메인 루프에서만 호출한다.
- 실행 모드당 모터 명령 생성자는 한 곳이다(생산은 FSM). 임의의 Running 안전 스냅샷을 꾸며 우회하지 않는다.
- 모터 테스트는 낮은 출력으로 모터별 3초씩만 구동한다. 실물 시험은 먼저 바퀴를 바닥에서 띄우고 진행한다.

## 카메라 및 라즈베리파이 통신 요구사항

- 카메라는 로봇 전방을 향하며 중앙 부근에서 약간 아래쪽을 본다.
- 라즈베리파이가 컬러 타워를 영상에서 검출하고, ESP32에는 프레임 안 타워 좌표만 UART1으로 전달한다.
- 사용자가 최초 설명에서 해상도/프레임을 `19220*1080, 50F`로 적었다. 의도는 `1920x1080, 50 FPS`로 추정되지만 구현 전 확인이 필요하다.
- 패킷 V1은 14바이트 고정 길이, 리틀 엔디언이다. 바이트 배치·상태 비트·범위의 원본은
  `include/communication/vision_protocol.hpp`, 설명과 예시는 README §10이다.
- 라즈베리파이-ESP32 고정 배선은 신뢰도가 충분하다는 사용자 판단에 따라 CRC를 넣지 않는다.
- 라즈베리파이는 새 영상 프레임을 처리할 때마다 `sequence`를 1 증가시키며 `255 -> 0` 순환을 허용한다.
  같은 처리 결과를 재전송할 때는 sequence를 증가시키지 않는다.
- 라즈베리파이는 50Hz 고정 주기로 영상처리 결과를 일방적으로 전송한다. ESP32는 주기를 만들거나 재전송을 요청하지 않는다.
- 목표가 없어도 카메라와 처리 파이프라인이 정상이라면 50Hz로 계속 패킷을 보낸다.
  목표가 없으면 좌표와 박스 크기는 모두 0이고 bit0~3도 모두 0이어야 한다.
- ESP32 파서는 블로킹 없이 헤더, 버전, 길이, 상태 조합, 좌표와 크기를 검사한다.
  정상 패킷이 없으면 `linkValid=false`, 새 sequence가 없으면 `frameFresh=false`가 된다(시간은 `config.hpp`).
  통신은 살아 있어도 같은 sequence만 반복되면 영상 처리 정지로 판단한다.
- 라즈베리파이는 주행 필수 장치가 아니다. 미연결, 재부팅, 통신 끊김은 예상된
  상황이며 시스템 고장이나 모터 금지 조건으로 사용하지 않는다. 구동 FSM이
  `VisionSnapshot::linkValid`와 `frameFresh`를 확인해 비전 없이 가능한 탐색 등 다른 주행 로직으로 전환한다.

## 컬러 센서 및 TCA9548A

- AS7341은 차량 네 모서리에 1개씩, 총 4개다. 동일 I2C 주소 충돌을 피하기 위해 TCA9548A를 사용한다.
- AS7341은 F2/F3/F5/F6/F7/Clear를 단일 묶음 연속 측정한다. F1/F4/F8/NIR은 미측정이다.
- 생산 코드에서는 `include/sensors/sensor_config.hpp`의 `COLOR_SENSOR_MODEL` 한 줄로
  AS7341 또는 TCS34725를 선택한다. 두 센서는 동일한 TCA 채널과 모서리 순서를 쓴다.
- 수광 시간, 게인, LED 전류는 같은 설정 파일에서 조정한다. 이 값이 달라지면 기존 캘리브레이션은
  자동으로 무효 처리한다.
- 동일한 색이 `COLOR_CONFIRM_COUNT`회 연속 판정되어야 신뢰 가능한 색으로 공개한다. 기본값은 3회다.
- 센서 주기는 최종 확정하지 않았으며 두 센서의 수광 시간별 시험 후 설정한다.
- 저장된 캘리브레이션이 없어도 하드코딩된 임시 임계값으로 부팅과 판정을 계속한다.
  센서 초기화 실패도 부팅을 막지 않으며 해당 센서만 `Unknown`으로 남긴다.
- 수광 완료를 기다리는 라이브러리 호출 대신 짧은 Wire 레지스터 단계로 진행한다.
  AS7341은 ASTATUS부터 연속 읽어 ADC 데이터를 래치하고 포화도 확인한다.
  AS7341은 한 묶음의 Clear로 비율을 정규화한다. APERS=0의 AINT 완료 이벤트를
  확인·소거하고 최소 수광 간격도 확인하며, AVALID만으로 새 샘플을 세지 않는다.
- I2C/수광 타임아웃 오류 채널은 재부팅 전까지 비활성화한다. 다른 채널은 계속 읽는다.
  무수광/포화는 해당 측정만 무효이며 재초기화하지 않고 다음 정상 측정을 진행한다.
- `FloorColorClassifier`, `CalibrationStore`(NVS 읽기·저장), `ColorCalibration`(교정 절차)은 별도 파일로 유지한다.
- 기체에 추가 가림막/구조물을 설치할 수 없다. 자체 LED로 비추며 10mm 단차 때문에
  센서-바닥 간격은 3/10/20mm로 변한다. 고정 높이로 가정하지 않는다.
  근접 포화, 20mm 유색 바닥의 검정 오인, 경계 혼합을 고려하고 다음 작업에서도
  이 조건을 고려하고 있음을 사용자에게 설명한다. 상세 설정과 미검증 사항은 README §7·§8을 읽는다.
- 교정은 생산 펌웨어에 넣지 않는다. 별도 환경 `color_calibration`을 업로드해 진행하고,
  `CAL SAVE` 후 생산 펌웨어를 다시 업로드한다. 생산 펌웨어는 `CalibrationStore::load()`로 NVS 값만 읽는다.
- 교정 펌웨어는 모터를 초기화하지 않고 BTS7960 PWM/EN 핀을 LOW로만 고정한다. 그래도 모터 전원은 분리한다.
- 교정은 센서별로 빨강/노랑/파랑/검정과 평행10mm/들림20mm/눌림3mm를 각각 3초 측정한다(48단계).
  NVS 형식(magic, version, 설정 서명)은 두 펌웨어가 공유하므로 한쪽만 바꾸지 않는다. 명령 목록은 README §9.

## 시스템 상태 관리자

- `SystemManager`가 SW2 해제 이벤트를 단독으로 소비하고 모터 허용 여부를 결정한다.
  다른 모듈은 버튼을 직접 운전 상태로 해석하지 않고 `SystemStatus` 또는 `SafetyStatus`를 조회한다.
  안전 상태의 원본은 `SystemManager` 하나만 둔다.
- 상태는 Booting, WaitingForStart, Running, SensorFault, MotorFault, SystemFault,
  EmergencyStop이다(`system_manager.hpp`). `Calibration` 값은 로그 번호 유지를 위한 예약값이며 진입하지 않는다.
- 라즈 UART 패킷 파서는 시스템 상태 관리자와 분리되어 있다. 라즈 상태는
  `RaspberryLink::latest()`로 구동 FSM에서만 판단한다. 라즈가 없거나 끊겨도
  `SystemManager`의 상태와 모터 허용 여부는 바뀌지 않는다.
- 건전성이 `false`가 되면 즉시 모터 정지와 고장 상태 전환을 하고 시작 요청도 폐기한다.
  건전성을 나중에 `true`로 보고하더라도 자동 재출발하지 않는다.
- V1 컬러 센서의 개별 오류는 이 집계 고장에 연결하지 않고 해당 채널의 오류와 Unknown만 남긴다.
- SW2는 시작 기능만 하며 다시 누른다고 정지하지 않는다. 정지는 `requestStop()`으로만 요청한다.

## 로그와 LED

- 이벤트 로그는 고정 크기 큐이며 `process()` 한 번에 출력하는 개수가 제한된다. UART 송신을 기다리지 않는다.
- 큐 드롭은 별도 로그를 다시 만들지 않고 `status()` 값으로만 확인한다.
- ISR에서는 로거를 직접 호출하지 않고 플래그만 남긴 뒤 일반 태스크에서 호출한다.
- 이벤트 번호 범위는 고정한다: 100 부팅/시스템, 200 FSM 상태/모드, 300 통신, 400 센서,
  500 모터, 600 안전, 900 사용자 정의. 형식과 API는 `event_logger.hpp`와 README §12.
- 상태, 모드, 오류는 변경 감지 API로 값이 실제로 달라졌을 때만 기록한다.
  빠르게 변하는 측정값으로 중복 제한을 우회하지 않는다.
- ESTOP에 들어가면 기존 큐를 폐기하고 이후 일반 로그를 거부하며 `ESTOP`만 3초마다 출력한다.
- LED 출력은 낮은 우선순위 `update()`에서만 실행한다. 호출 주체별 요청을 보존하고 우선순위가 높은 상태를 표시한다.

## 메인 루프와 FSM

- `src/main.cpp`는 안전 관리자와 모터 워치독을 가장 먼저 갱신한다. 실행 순서는 MAP.md §3.
- 라즈베리파이 패킷과 네 컬러 센서를 비블로킹 방식으로 갱신한다.
- FSM 우선순위는 안전 정지, 색상 위험구역 회피, 목표 확인·정렬·접근,
  돌진·급정지·스포크 삽입·밀기, 비전이 없을 때 탐색 순서다.
- 앞뒤 센서가 동시에 위험색이면 짧게 브레이크한 뒤 마지막으로 한쪽 끝만 위험색이었던 방향의
  반대로 빠져나온다. 기록이 없으면 Backoff 중 진입은 전진, 그 외는 후진이며 일정 시간마다 방향을 뒤집는다.
  홈 안에서 계속 정지하지 않는다(10초 규정).
- 공격 시퀀스가 시작되면 짧은 카메라 가림에는 중단하지 않는다. 시간 값은 `control_config.hpp`,
  상태 흐름 설명은 README §6.

## 별도 펌웨어 환경

- 보드에는 생산(`yd_esp32_s3`), 벤치(`robot_bench`), 센서 점검(`sensor_serial_test`),
  교정(`color_calibration`) 중 하나만 업로드한다.
  환경 목록은 README §2.
- 센서 점검 펌웨어는 모터 핀을 건드리지 않는다. 센서 시험 중에는 모터 전원을 분리한다.
- 벤치 펌웨어는 생산 FSM을 실행하지 않는다. 모드 변경 시 정지 후 SW2로 재시작해야 하고,
  수동 DRIVE는 250ms 유지 제한, 시험 출력은 최대 20%다. 상세 사용법은 BENCH_TESTS.md.
- 하드웨어 없는 실제 소스 자동 검증은 `tests/run_host_tests.ps1`로 실행한다.
  이 검증은 전기적 브레이크나 실제 ESP32 스케줄링/센서 수광의 실물 검증이 아니다.
- PlatformIO 보드는 범용 `esp32-s3-devkitc-1`로 설정되어 있다. 실제 YD-ESP32-S3의 플래시 및
  PSRAM 용량은 아직 확인하지 않았으며, 해당 기능을 사용하기 전에 보드 옵션을 맞춰야 한다.

## 대회 규정에서 펌웨어에 직접 영향을 주는 내용

원본 규정 파일은 저장소 루트의 `2026년 IRC 씨름 로봇 규정-20260511.pdf`다.

- 로봇은 완전 자율주행이어야 하며 경기 중 리모컨을 사용할 수 없다.
- 카메라는 최대 2대다.
- 스위치는 ON/OFF 전원 인가 목적으로만 사용해야 하며 방향이나 전략을 선택하는 입력으로 쓰면 안 된다.
- 경기 시작 전에 로봇 전원이 들어와 있어도 되지만 구동장치가 움직이면 안 된다.
- 경기 시작 시 팀장은 구동 스위치만 조작할 수 있다.
- 안전스위치는 전략 입력이 아니라 안전 정지 기능으로만 사용한다.
- 경기장 바닥은 검은색이고 빨간색 중앙 홈, 파란색 모서리 홈, 노란색 직사각형 홈이 있다.
- 홈 깊이는 10mm이며 노란색 홈은 득점 구역이 아니지만 높이 차가 존재한다.
- 로봇이 홈에서 10초 안에 빠져나오지 못하거나 작동 불능이 되면 경기상 불이익이 있다.
