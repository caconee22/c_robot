# 현장 팀원용 펌웨어 안내서

코딩을 몰라도 Claude나 Codex에게 정확히 요청하고, AI가 잘못 고치려 할 때 알아챌 수 있도록 쓴 문서다.
처음 한 번은 끝까지 읽고, 이후에는 필요한 절만 찾아본다.

AI에게는 작업을 시작할 때 이렇게 말한다.

> `ESP_MAIN/TEAM_GUIDE.md`, `ESP_MAIN/MAP.md`, `ESP_MAIN/AGENTS.md`를 먼저 읽고 시작해.
> 나는 코딩을 모르니까 바꾸기 전에 무엇을 왜 바꾸는지 먼저 설명하고, 내가 좋다고 하면 바꿔.

## 1. 로봇 한눈에 보기

```text
              앞 (카메라)
        S1 앞왼쪽      S2 앞오른쪽
        왼쪽 모터      오른쪽 모터
        S3 뒤왼쪽      S4 뒤오른쪽
              뒤
```

| 부품 | 역할 |
|---|---|
| ESP32-S3 (YD-ESP32-S3) | 로봇의 두뇌. 이 폴더의 코드가 여기서 돈다 |
| BTS7960 두 개 | 왼쪽·오른쪽 모터 드라이버 |
| 컬러 센서 4개 (AS7341) | 네 모서리에서 바닥 색을 본다. 검정=정상 바닥, 빨강·노랑·파랑=홈(피할 곳) |
| TCA9548A | 같은 주소의 센서 4개를 하나씩 골라 읽게 해 주는 분배기 |
| 라즈베리파이 + 카메라 | 상대 타워를 찾아 화면 좌표만 ESP32로 보낸다 |
| SW1 (빨간 안전 스위치) | 누르면 즉시 영구 정지. **재부팅 전까지 절대 다시 안 움직인다** |
| SW2 (시작 버튼) | 눌렀다 떼면 출발. 다시 눌러도 멈추지 않는다 |
| LED 2개 | 현재 상태 표시 (5절 참고) |

V1 로봇에는 **IMU(기울기), 거리 센서, 적외선 센서, 엔코더, 전류 센서, 배터리 측정이 없다.**
AI가 "거리 센서를 쓰면 됩니다", "IMU로 기울기를 확인하면 됩니다"라고 하면 틀린 제안이다.

## 2. 업로드하는 펌웨어 4종류

보드에는 **한 번에 하나만** 올린다. 목적에 맞는 것을 고른다.

| 이름 (환경) | 언제 쓰나 | 모터 | UART0 속도 |
|---|---|---|---:|
| `yd_esp32_s3` | **경기용.** 평소에는 이것 | 움직임 | 57600 |
| `robot_bench` | 바퀴 띄우고 모터·회피를 낮은 출력으로 시험 | 최대 20% | 57600 |
| `sensor_serial_test` | 센서 4개 원시값만 확인 | 안 씀 | 115200 |
| `color_calibration` | 바닥 색 교정 (48단계) 후 저장 | 안 씀 | 57600 |

TCS34725 센서를 쓰는 차량이면 이름 뒤에 `_tcs34725`가 붙은 환경을 쓴다.
**V2 기판**에는 이름 뒤에 `_v2`가 붙은 환경을 쓴다 (예: `yd_esp32_s3_v2`). V1 기판에 V2 펌웨어를 올리거나
그 반대로 하면 모터 핀이 달라 위험하다. 기판 버전을 먼저 확인한다.

VS Code의 PlatformIO 터미널에서 실행한다.

```powershell
cd D:\C_ROBOT\ESP_MAIN
pio run -e yd_esp32_s3 -t upload        # 경기용 올리기
pio device monitor -b 57600             # 로그 보기
```

`sensor_serial_test`와 `color_calibration`은 모터를 켜지 않지만 **모터 전원은 분리하고** 쓴다.
교정을 마치면 반드시 `yd_esp32_s3`를 다시 올려야 주행한다.

## 3. 코드 구조 — 무엇을 바꾸려면 어디를 보나

`include/`는 "무엇을 할 수 있는지(설명서)", `src/`는 "실제로 어떻게 하는지(구현)"다.
각 헤더(`.hpp`) 맨 위의 `// Contract` 주석에 그 모듈의 역할이 적혀 있다.

| 하고 싶은 일 | 볼 파일 |
|---|---|
| 주행 속도, 공격 시간, 회피 시간 바꾸기 | `include/control/control_config.hpp` |
| 상황별 행동(언제 공격·회피·탐색) 바꾸기 | `src/control/robot_fsm.cpp` |
| 센서 밝기·게인·LED 전류, 색 판정 기준 바꾸기 | `include/sensors/sensor_config.hpp` |
| 모터 최대 출력, 모터 방향 뒤집기, 브레이크 방식 | `include/motor/motor_config.hpp` |
| 핀 번호 확인 (바꾸지 않는다) | `include/pins.hpp` |
| 전체 실행 순서 | `src/main.cpp` |

설정값 숫자는 `*_config.hpp` 파일 한 곳에만 있다. 대부분의 튜닝은 이 파일들의 숫자만 바꾸면 된다.

## 4. 작동 방식

### 전원을 켜면

```text
모터 핀 LOW로 고정 → 모터 준비 → 버튼 → LED → 센서 → 라즈 통신 → 안전 관리자
→ 시작 대기 (LED 주황 점멸)
→ SW2를 눌렀다 떼면 출발
```

- 센서가 고장 나거나 라즈가 연결되지 않아도 **부팅은 된다.** 모터 준비에 실패하면 출발하지 않는다.
- 전원을 켤 때 SW2를 누르고 있었다면 그 버튼은 무시된다. 한 번 뗐다가 다시 눌렀다 떼야 출발한다.

### 주행 중 매 순간 반복 (`loop()`)

```text
안전 확인 → 라즈 좌표 받기 → 센서 읽기 → 안전 다시 확인
→ FSM이 행동 결정 → 좌우 모터 값으로 변환 → 모터 출력 → LED·로그
```

### 모터를 멈추는 길은 세 가지이고 서로 독립이다

1. **SW1:** 버튼 인터럽트가 모터 드라이버 EN을 그 순간 끊는다. 재부팅 전 복구 없음.
2. **안전 관리자:** 고장이 보고되면 정지하고 출발 요청을 지운다. 다시 SW2를 눌러야 한다.
3. **명령 만료 감시:** 메인 루프가 멈춰 모터 명령이 100ms 동안 갱신되지 않으면 정지한다.

### FSM — 로봇이 상황마다 하는 행동

우선순위가 위일수록 먼저 판단한다.

| 순위 | 상황 | 행동 |
|---:|---|---|
| 1 | 출발 전, 고장, SW1 | 브레이크 |
| 2 | 센서가 빨강·노랑·파랑 홈을 확정 | 홈 반대 방향으로 탈출 (공격 중이어도 끊고 탈출) |
| 2-1 | 앞뒤 센서가 동시에 홈 | 150ms 정지 → 마지막에 들어간 쪽 반대로 빠져나옴 → 1.5초마다 방향 전환 |
| 3 | 공격 진행 중 | 돌진 220ms → 급정지 90ms → 스포크 삽입 350ms → 밀기 |
| 4 | 타워가 보임 | 2프레임 확인 → 정렬(회전) → 접근 → 충분히 크고 중앙이면 공격 시작 |
| 5 | 타워를 방금 놓침 | 0.26초 동안 마지막 방향으로 회전 |
| 6 | 아무것도 안 보임 | 제자리 회전 탐색 (1.2초마다 방향 바꿈) |

공격은 **시간으로만** 진행한다. 실제로 상대 밑에 들어갔는지 확인하는 센서는 없다.

## 5. LED 색 읽는 법

| LED | 의미 |
|---|---|
| 파랑 점멸 | 부팅 중 |
| 주황 점멸 | 시작 대기 (SW2를 누르면 출발) |
| 빨강 고정 | **SW1 비상정지. 재부팅해야 함** |
| 빨강/흰색 빠른 교대 | 시스템 고장 |
| 빨강/주황 빠른 교대 | 모터 고장 |
| 빨강 점멸 | 탐색 중 (타워 못 찾음) |
| 초록 고정 | 타워 확인 중 |
| 노랑 고정 | 타워 쪽으로 회전 정렬 중 |
| 청록 고정 | 타워에 접근 중 |
| 흰색 매우 빠른 점멸 | 돌진 |
| 파랑 고정 | 밀기 (출발 직후 탐색 전 잠깐도 파랑일 수 있음) |
| 주황 빠른 점멸 | 홈 회피 또는 후진 |
| 보라 점멸 | **타워를 잠깐 놓침** (통신 끊김 표시가 아님) |

## 6. 의도된 설계 — 버그처럼 보여도 고치지 않는다

AI가 아래 항목을 "문제"라고 하면 이 표를 보여 주고 거절한다.

| 보이는 모습 | 이유 |
|---|---|
| SW1을 놓아도 다시 안 움직임 | 안전 규칙. 재부팅해야만 복구된다 |
| SW2를 다시 눌러도 안 멈춤 | SW2는 시작 전용. 대회 규정상 스위치로 전략을 바꿀 수 없다 |
| 라즈 통신에 CRC(오류 검사)가 없음 | 짧은 고정 배선이라 일부러 뺐다. 헤더·길이·범위·순번으로 검사한다 |
| 라즈가 꺼져도 고장이 아님 | 영상 없이도 탐색·회피는 해야 한다 |
| 센서 하나가 고장 나도 출발함 | 그 센서만 "모름"으로 두고 나머지로 주행한다. 자동 재연결은 하지 않는다 |
| `SystemManager::update()`를 한 루프에 두 번 부름 | 센서·통신 처리 사이에 생긴 위험을 다시 잡으려는 것. 합치지 않는다 |
| 코드에 `delay()`를 거의 안 씀, 센서를 조금씩 나눠 읽음 | 메인 루프를 오래 멈추면 안전 확인과 모터 갱신이 늦어진다 |
| 교정이 생산 펌웨어에 없음 | 교정은 `color_calibration` 펌웨어를 따로 올려서 한다 |
| 색이 3번 연속 같아야 인정 | 경계·잡음 오판을 줄이기 위한 최소 횟수. 3 미만은 빌드가 거부한다 |
| 쓰지 않는 상태 이름이 있음 (ContactCheck, WallEscape 등) | 나중을 위한 예약. 지금은 들어가지 않는다 |
| 모터 출력이 65%로 제한됨 | 시작값. 실물 시험 후 올릴 수 있지만 상한 1000을 넘을 수 없다 |

## 7. 할 수 없는 것과 알려진 한계

| 한계 | 결과 |
|---|---|
| 바닥까지 높이를 재지 못함 | 센서-바닥 간격이 3mm(눌림)·10mm(평소)·20mm(홈에 걸침)로 변해도 모른다 |
| 20mm에서 홈 색이 어두워짐 | **빨강·파랑 홈이 검정으로 읽혀 회피를 못 할 수 있다.** 실측과 교정이 필요하다 |
| 3mm에서 너무 밝음 | 센서 값이 꽉 차서(포화) 그 측정은 버려진다 |
| 색 경계 위 | 두 색이 섞여 "모름"이 될 수 있다 |
| 교정 안 하면 임시 기준 사용 | 임시 기준은 어두우면 무조건 검정으로 본다. 경기 전에 반드시 교정 |
| 센서 설정(수광·게인·LED)을 바꾸면 | 기존 교정이 자동으로 무효가 된다. 다시 교정해야 한다 |
| 상대와의 거리를 모름 | 화면 속 타워 박스 높이로 대략 판단할 뿐이다 |
| 공격 성공을 확인 못 함 | 시간에 맞춰 돌진·삽입·밀기를 할 뿐이다 |
| 아무것도 안 보이면 제자리 회전만 | 전진하며 찾는 동작은 아직 없다 |
| 밀기 중 조향이 약함 | 650 출력에 조향을 더하면 상한에 걸려 조향 효과가 절반이 된다 |
| 색 3번 확인에 시간이 걸림 | 0.5m/s에서 최소 약 1cm 이동 후 판단. 제동 거리는 별도 |

**아직 실물로 확인하지 못한 것**

- 브레이크 전기 조합 (`BRAKE_STRATEGY`). 바퀴를 띄우고 먼저 확인한다
- 각 모터의 앞·뒤 방향 (`LEFT_MOTOR_INVERTED`, `RIGHT_MOTOR_INVERTED`)
- TCA 채널 순서가 실제 배선과 맞는지 (S1~S4 = 채널 0~3으로 가정)
- 수광 5ms, 게인 X16, LED 20mA (전부 시작값)
- 공격·회피 시간과 출력값 전부
- **라즈베리파이 쪽 14바이트 UART 송신 코드가 아직 없다.** 그래서 타워 추적·공격은 실물에서 동작한 적이 없다

## 9. AI가 제안해도 거절할 것

- **Wi-Fi** 켜기 (무선 업로드, 웹 화면, 무선 조종 등 전부)
- **외부 플래시·PSRAM** 켜기
- **USB** 포트 사용 (업로드와 로그는 UART 포트로만)
- 엔코더 사용 (V2 기판에 핀은 있지만 쓰지 않기로 했다)
- 핀 번호(`pins.hpp`) 변경
- SW1 비상정지, SW2 시작 절차, 명령 만료 감시를 없애거나 단순화하거나 합치기
- 라즈 통신 형식 변경, CRC·ACK·재전송 추가
- 고장 시 자동 재부팅, 센서 자동 재초기화, 무한 재연결 추가
- 메인 루프에 긴 `delay()`, 측정 완료를 기다리는 코드 추가
- 새 RTOS 태스크로 기능 쪼개기
- 파일 대이동, 이름 일괄 변경, 대규모 정리
- 가림막·IMU·거리 센서처럼 로봇에 없는 부품을 전제로 한 해결책

AI가 이런 걸 하겠다고 하면 "AGENTS.md 규칙 위반이니 하지 마"라고 말한다.

## 10. 현장 첫 작업 순서

1. **센서 확인:** 모터 전원 분리 → `sensor_serial_test` 업로드 → 115200으로 모니터 → S1~S4 값이 나오는지, 손으로 가리면 어느 센서 값이 변하는지 확인 (채널 순서 확인).
2. **센서 실측:** 네 모서리 × 네 색 × 3/10/20mm 원시값을 기록. 특히 20mm 빨강·파랑이 검정과 구분되는지.
3. **교정:** `color_calibration` 업로드 → 57600 모니터 → `CAL START` → 안내대로 48단계 → `CAL SAVE`.
4. **모터 확인:** 바퀴를 띄움 → `robot_bench` 업로드 → BENCH_TESTS.md 순서대로 모터 방향·브레이크·SW1 확인.
5. **경기 펌웨어:** `yd_esp32_s3` 업로드 → 바퀴 띄운 채 SW2 → 회전 탐색 확인 → 바닥에서 낮은 속도부터.

각 단계 결과(사진, 로그, 숫자)는 원격 팀원에게 보낸다.

## 11. AI에게 요청하는 법

**좋은 요청**

- "탐색 회전이 너무 빨라. `SEARCH_DUTY`를 300에서 220으로 바꿔줘. 다른 건 건드리지 마."
- "홈 회피할 때 후진이 짧아서 다시 홈에 걸려. 관련 값이 뭐고 어떻게 바꾸면 되는지 먼저 설명해줘."
- "이 로그를 보고 왜 출발을 안 했는지 설명해줘." (로그를 붙여 넣는다)

**나쁜 요청**

- "코드 좋게 고쳐줘" → AI가 안전 코드까지 손댈 수 있다
- "에러 나니까 알아서 다 고쳐줘" → 무엇이 바뀌었는지 모르게 된다

**바꾼 뒤 확인** (AI에게 실행해 달라고 하면 된다)

```powershell
.\tests\run_host_tests.ps1     # PC 시험. 끝에 "checks passed"가 나와야 함
pio run -e yd_esp32_s3          # 빌드. SUCCESS가 나와야 함
```

PC 시험 통과는 "코드 논리가 안 깨졌다"는 뜻일 뿐이고, 실제 로봇 동작을 보장하지 않는다.

**바꾼 내용은 Git으로 남긴다.** AI에게 "새 브랜치 만들어서 커밋하고 푸시해줘"라고 하면 원격 팀원이 확인할 수 있다.
`main`에 바로 올리지 말고 브랜치로 올린다.

## V2 기판 첫 시험 (오른쪽 모터 EN 확인)

V2 기판의 오른쪽 모터 EN(GPIO35)은 보드 안의 메모리와 핀을 같이 쓴다. 처음 한 번은 반드시 확인한다.

1. 모터 전원을 분리하고 `sensor_serial_test_v2`나 `robot_bench_v2`를 올린다.
2. EN_2 선에 LED(저항 포함)나 측정기를 연결하고 전원을 껐다 켜고, 리셋 버튼도 눌러 본다.
   **켜지는 순간 LED가 깜빡이면 문제**다.
3. 벤치에서 오른쪽 모터를 켜고 끌 때 EN_2가 따라오는지, SW1을 누르면 즉시 꺼지는지 본다.
4. 문제가 있으면 원격 팀원에게 알린다. 해결책은 EN_2 선을 GPIO38로 옮기고
   `include/pins_v2.hpp`의 `MOTOR2_EN` 한 줄을 `GPIO_NUM_38`로 바꾸는 것이다.

## 12. 문제가 생겼을 때

| 증상 | 확인할 것 |
|---|---|
| 전원 켰는데 LED가 빨강 고정 | SW1이 눌려 있다. SW1을 풀고 재부팅 |
| 주황 점멸에서 출발 안 함 | SW2를 확실히 눌렀다가 완전히 뗐는지. 전원 켤 때 누르고 있었으면 한 번 더 |
| 출발했다가 바로 멈춤 | 로그에서 `503`(명령 만료)이나 `500`(모터 고장)이 있는지, `ESTOP`만 반복되는지 |
| 모터 하나가 반대로 돎 | `motor_config.hpp`의 `*_MOTOR_INVERTED` |
| 홈을 지나쳐 들어감 | 센서 실측·교정 상태, 20mm 검정 오인 가능성 |
| 검정 바닥에서 계속 회피함 | 교정 상태, 센서 하나의 값만 이상한지 |
| 타워를 봐도 반응 없음 | 라즈 송신기가 연결됐는지, 로그 `303` 값이 3인지 |
| 빌드 실패 | 오류 메시지 전체를 AI에게 붙여 넣는다 |

### 로그 형식 (UART0 57600)

```text
EV,시간ms,이벤트번호,심각도,소스,값1,값2[,문자열]
```

| 번호 | 의미 |
|---:|---|
| 101 / 102 | 부팅 완료 / 부팅 실패 |
| 200 | FSM 상태 변경 (값1 = 상태 번호, 아래 표) |
| 202 / 203 | 주행 시작 / 주행 정지 |
| 204 | 시스템 상태 변경 (0 부팅, 1 대기, 2 주행, 4 센서 고장, 5 모터 고장, 6 시스템 고장, 7 비상정지) |
| 302 | 라즈 패킷 오류 (값1 = 오류 종류) |
| 303 | 라즈 상태 (값1: 0 없음, 1 연결만, 3 연결+새 영상) |
| 400 / 401 | 센서 고장 발생 / 해제 (값2 = 센서 번호 1~4) |
| 500 / 501 | 모터 고장 발생 / 해제 (값1 = 고장 종류) |
| 503 | 모터 명령 만료로 정지 |

SW1 비상정지가 걸리면 일반 로그는 멈추고 `ESTOP` 한 줄만 3초마다 나온다.

FSM 상태 번호: 1 대기, 2 탐색, 3 타워 확인, 4 정렬, 5 접근, 7 돌진, 8 급정지, 9 스포크 삽입,
11 밀기, 13 후진, 14 타워 놓침, 16 홈 회피, 18 비상정지.
